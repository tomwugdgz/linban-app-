# 门禁决策记录（Gate Decisions）

> **类型**：门禁**取舍**的留痕。每条记「决定了什么 / 为什么这么定 / 谁裁的 / 怎么被验证过」。
>
> **为什么需要这个文件**：门禁脚本文件头记的是「覆盖什么 / 不覆盖什么」——
> 那是**能力边界**。本文件记的是**主动做出的取舍**：明明能查却故意不查、
> 明明会红却刻意留着、明明是 bug 却判定为噪音。
> 后者比前者危险 —— 因为前者是「不知道」，后者是「知道了但选了不查」，后来人会误以为「查过了，没事」。
>
> **归属**：宋砚秋（Cyrus Ledger）｜rnd-linban 研发部｜数据库设计与优化
> **维护约定**：新增决策追加在末尾，**不修改历史条目**（历史决策的上下文不可追改）。

## D-001 · 段 5 规则 A 的已知噪音：刻意**不豁免**

| 项 | 内容 |
|---|---|
| **决策** | `verify-doc-configs.ts` 段 5 规则 A 对 `docs/DATABASE.md:789` 持续报 WARN，**刻意保留、不加豁免、不改文案** |
| **裁 定 人** | team-lead（2026-10，「裁定**不加豁免**」） |
| **执行 人** | 宋砚秋 |

### 一、现象

`npm run doc:check:configs` 每次运行稳定输出：

```
[WARN] docs/DATABASE.md:789 状态性表述 待承钧 — ⚠️ 最近的迁移 **已在磁盘**:
       20261022040000_a7_communities
→ 需人工核对：文档说未做、磁盘已做？
```

### 二、判定：**误报**（不是真漂移）

依据是该行（`docs/DATABASE.md:789`，§13 变更记录 #11 · A7 落盘）原文**两处并存**：

- 「迁移 `20261022040000_a7_communities` **已生成**并经迁移链漂移校验（exit=0）」
- 「**遗留三处非 schema 改动待承钧/映棠处理**：`admin.service.ts` 三处 / `HealthBoardPage.tsx` / `seed.ts`」

即：**迁移本身已落且文档已如实声明**；待办指的是**代码侧**三处，与迁移无关。
规则 A 触发的原因是它把「同行的迁移名」当成了「状态词所指的对象」——
一个**同名不同指**的误配。

### 三、为什么不豁免（这是本决策的核心）

1. **豁免机制本身是门禁的可信度折损。** 每加一条豁免，就多一个「这里为什么不管」
   需要后来人重新判断一次。豁免清单本身就是一份「已知不查项」的债。
2. **一旦为自家文档开白名单，规则 A 就不再是通用检查。** 这条规则是我写的，
   我的文档是它的主要检查对象 —— 给自己的文档开豁免，等于让门禁只查别人不查自己。
3. **WARN 的定位就是「提醒但不挡人」。** 一条永远存在的 WARN 是可接受的
   （每次运行提醒读者去看一眼那一句），一条被豁免的 WARN **等于不存在**。
4. **段 5 本来就是弱规则**（只报 WARN、不计入退出码）—— 噪音的代价已被设计压到最低，
   而真实矛盾的可见性是这个设计存在的全部理由。

### 四、**若将来这类噪音变多，该改的是规则语义，不是加白名单**

正确方向：让规则判断「状态词与迁移名是否指同一对象」，而不是维护一份豁免清单。
错误方向：再往豁免列表里加一行。

### 五、怎么被验证过

- **正向**：改动文案或豁免逻辑 → 脚本复跑 → 观察输出
- **反向（规则 B 侧）**：注入外部假迁移名 `20261022999999_external_sync_from_other_system`
  → 规则 B 抓到 → 撤掉后 WARN 消失 → 证明「规则会响」不是空转
- **段 5 整体定位**：弱规则、只报 WARN、不计入退出码，判断权留给人

### 六、相关落点

- 门禁脚本文件头「**不覆盖**」清单末条已记本决策（脚本自解释，不依赖本文档）
- `docs/DATABASE.md` §13 变更记录 #17 记本轮联动

## D-002 · 探针留用但「不得被引用」由断言钉住

| 项 | 内容 |
|---|---|
| **决策** | 一次性诊断探针**保留**在 `apps/server/scripts/probes/`，但**不得被任何 `package.json` 的 script 引用** —— 由 `verify-doc-configs.ts` 段 6.8 断言 |
| **裁 定 人** | team-lead（2026-10，「探针脚本要留，但必须改名 + 加禁止执行标记」） |
| **执行 人** | 宋砚秋（断言部分）｜探针改名与标记由 team-lead 执行 |

### 一、为什么留而不删

探针记录的是「**当时怎么定位到问题的**」—— 删了就丢了排查路径。
下一任接手的人遇到同类问题时，探针是「已知这条思路走通过」的唯一线索。

### 二、为什么必须加断言（而不是靠人记住）

探针躺在 `scripts/` 目录时，**任何人看到都可能当成正式门禁去执行**。
「靠人记住别执行」不是工程手段。段 6.8 把这条纪律变成**可执行的检查**：

```
[PASS] 6.8 探针（2 个: probe-enum-collect.ts, probe-zod-group-p0.ts）
             未被任何 package.json 的 script 引用
```

破坏时：`[FAIL] 6.8 探针被 npm script 引用 1 处: apps/server/package.json → probe-zod-group-p0.ts` → **EXIT=1**。

### 三、连带记一条方法论（比断言本身更值钱）

**给 6.8 做反向验证时，我的第一次注入静默失败了。**

注入方式是把 `package.json` 里的 `"smoke":` 替换成指向探针的 script ——
但 **server 的 package.json 根本没有 `smoke` 键**，替换没发生，
而门禁当然不会红。我差点把这个结果误读成「6.8 是恒真断言」。

改法（已固化为注入脚本的守卫）：

```js
if (s.length === before) { console.error('替换失败'); process.exit(1); }
```

**推论：反向验证的「不红」有两种可能 ——「断言没牙齿」与「注入没生效」——
必须先把第二种排除，否则会把一个本来正确的断言改坏。**

这条与脚本文件头「开发教训」第 1 条同源：
**把「我没测到的东西」当成「不存在的东西」。**

### 四、相关落点

- `apps/server/scripts/verify-doc-configs.ts` 段 6.8（断言）+ 文件头「覆盖六项」+ 开发教训第 4 条

## D-003 · 承钧「断言数据源优先级」裁定的可执行化

| 项 | 内容 |
|---|---|
| **决策** | 把「断言数据源优先级：`import 真实常量` > `运行时计算` > `正则扒源码`」从**信里的裁定**变成**可执行断言** —— 新增元门禁 `test-assertion-source-discipline.test.ts` |
| **裁 定 人** | 霍承钧（2026-10 提出）；宋砚秋落笔 |
| **执行 人** | 宋砚秋 |

### 一、为什么不能只写在 wiki 里

承钧的裁定原文：

> 断言数据源优先级：`import 真实常量` > `运行时计算` > `正则扒源码`。
> 越靠前越不怕格式变化；正则扒源码是最后手段，且必须配「正则必须匹配到非空块」的断言。

**这条裁定本身是对的。** 但本项目的历史反复证明一件事：
**写下来的纪律若没有可执行断言，下一轮就会漂** —— 这正是本文件存在的理由。
故把「形状」本身变成断言。

### 二、落地：元门禁 3 条

`apps/server/src/middlewares/test-assertion-source-discipline.test.ts`：

1. **测试源码里不得出现硬编码缩进量的正则**（如 `/\n {8}\}/`）
2. **本门禁自身不是空转**（自证：把正则喂「有病样本」，断言它会命中）——
   防止门禁恒真，这条是本轮踩坑的直接产物（见下）
3. **读源码的测试都留了「匹配不到就红」的守卫**（抠块空不得静默通过）

### 三、本轮我踩的坑（比门禁本身更值钱）

**第一版判定逻辑是错的，且错在「看起来很严谨」**：

```ts
// ❌ 第一版：以为「`{` 前有反斜杠就该排除」
if (before.includes('\\')) continue;
```

但源码里 `}` 通常是**转义**的（`\}`，因为它在正则里是量词语法），
而 `\{` 的反斜杠就在 `{` **前面** —— 于是真命中被当成误报排除，**门禁恒绿**。

反向验证时它没红，我先怀疑是**注入没生效**，改用 Edit 工具重做注入
（第一次用 python 注入，反斜杠被 shell 吃掉，注入内容失真 —— 与上轮同一个坑），
确认注入有效后它**仍然不红**，才定位到判定逻辑本身。

**修法**：只认「`\n` + `{数字}`」这个字面组合，**不看后续 `}` 是否转义**。

**教训（与 D-002 同源，但更具体）**：
> 反向验证的「不红」有两种可能 ——「断言没牙齿」与「注入没生效」。
> 但本例是**第三种**：「注入有效 + 断言确实没牙齿」——
> 而「断言没牙齿」的原因又是**判定逻辑自己写错了**。
> 所以反向验证要**三查**：注入生效了吗？门禁逻辑对吗？门禁覆盖到位吗？
> 少查一环，就会把一个坏门禁当成好门禁留下。

### 四、门禁自身的边界（刻意不做宽泛检查）

试过做「所有 `exec` 结果必须有守卫」的宽泛检查，**放弃**，理由：
- `while ((m = re.exec(x)) !== null)` 是循环形态，天然不需守卫
- `if (!m) continue` 可能是「换形态重试」也可能是「跳过」，
  机器分不清二者 —— 与段 5「弱规则只报 WARN」是同一个困境
- **机器分不清就别让它阻塞**（同 D-001 的原则）

实测全库 14 份读源码的测试，**未发现真静默通过**：
所有 `?? ''` 兜底后都跟着必红的断言；`revenue-endpoint-contract` 的
`if (!m) continue` 是「换下一种形态试」，末尾有 `throw new Error` 兜底。

### 五、顺带修掉的那一处真实脆性

`outbound-cipher-guard.test.ts:245` 原本写死 `\n {8}\}`（依赖被测文件缩进）。
已改为不依赖缩进的写法。

**对照实验**（同一次把被测文件缩进 +2 空格）：

| 写法 | 结果 |
|---|---|
| 旧（`\n {8}\}`） | **红**：`未找到 hit_detail 块` —— 但红因是「缩进变了」不是「密文泄漏了」 |
| 新（`\n\s*\}`） | **绿** —— 不受缩进影响 |

## D-004 · 66 条契约测试按「脆性」三档分诊（主理人 2026-10 裁定）

| 项 | 内容 |
|---|---|
| **决策** | 承钧提的两份契约测试（`revenue-endpoint-contract` 28 条 + `companion-income-contract` 38 条 = **66 条**）**不整份挪成运行时断言**，改为按主理人三问判据做 A/B/C 三档分诊；**A 档 1 处已改造** |
| **裁 定 人** | team-lead（2026-10，「不整份挪，按脆性分诊」） |
| **执行 人** | 宋砚秋 |

### 一、主理人给的三问判据（逐条过）

1. **这条断言在什么情况下会假红？** —— 改了被测代码的格式/缩进/命名风格就会红 → 脆，**必须改**
2. **它测的是「行为」还是「文本长相」？** —— 文本长相 → 改成行为断言或降级为 WARN
3. **它漏了会怎样？** —— 漏了会静默通过 → **必须留**，且要标为「不覆盖什么」

### 二、分诊结果

| 档 | 判据 | 数量 | 处置 |
|---|---|---|---|
| **A 档** | 脆 **且** 漏了会静默通过 | **1** | **已改造**（见下） |
| **B 档** | 扒源码但稳定 | 65 | 保留 + 顶部标注「本文件只保证源码文本匹配，不保证运行时行为」 |
| **C 档** | 纯文本长相、漏了不致命 | 0 | 无 |

**为什么 65 条是 B 档（实测依据，不是拍脑袋）**：
- 76 个 `toContain` 断言断言的都是**字面量字符串**（如 `"adminPermGuard('revenue:read')"`、`"'revenue:read'"`），
  **不含缩进量、不含跨行结构** → 改缩进/改命名风格**不会**让它们假红
- 13 个 `toMatch` 断言**全部**用 `\s*` / `[\s\S]` / 字面量，**无一处写死缩进量**
  （与 `outbound-cipher-guard.test.ts` 那处 `\n {8}\}` 不同形态）
- 「漏了会怎样」：66 条里**没有一条**是「抠块空但断言仍通过」的静默形态 ——
  所有 `?? ''` 兜底后都跟着必红的断言；`bodyOf` / `routeBlock` 等工具函数**找不到就 throw**

### 三、A 档那 1 处（已改造）：`routeBlock` 的降级截断

**位置**：`apps/server/src/middlewares/revenue-endpoint-contract.test.ts:12`

**原实现**：
```ts
const end = src.indexOf('\n);', idx);
return src.slice(start, end < 0 ? idx + 400 : end);   // ← 找不到终点就退化成固定 400 字符截断
```

**危害**（不是「脆」，是「**漏了会静默通过**」）：
本文件 `:118` 是**否定断言**：
```ts
expect(stripComments(routeBlock(routes, "'/activity/revenue'"))).not.toContain('risk:')
```
若 `routeBlock` 因找不到 `\n);` 而退化成 400 字符截断，**取样不全** →
`risk:read` 恰好在被截掉的后面 → **断言假通过，门禁全绿，而被测代码确实写了违规权限点**。

**同一批代码里两份文件做法相反**：`companion-income-contract.test.ts` 的同款函数
**早就是「找不到就 throw」**，且注释明确写了：
> 找不到就退化成固定长度截断 —— 那样「块内不含 X」的断言会因取样不全而**假通过**。
> 这类「因为工具切歪了所以断言没生效」与断言写错一样危险。

**本轮改造**：改成 `if (end < 0) throw new Error(...)`，与 companion 那份对齐。

### 四、A 档改造的对照实验（主理人要求的「改坏 → 红；改回 → 绿」）

构造双条件场景：**终点找不到**（路由收尾由 `);` 改成 `  );`，模拟 Prettier 格式化嵌套调用）
**且违规点在 400 字符之外**（在违规点前塞 420 字符注释）。

| 写法 | 否定断言 `not.toContain('risk:')` | 正面断言 `toContain('10001')` |
|---|---|---|
| **旧（降级截断）** | **假通过**（漏检，全绿） | 假红，但**红因误导**（"10001 不在截断片段里"） |
| **新（throw）** | **红**，红因 = 「未找到注册终点」 | **红**，红因 = 「未找到注册终点」 |

**新版的红因才是可操作的** —— 它直接告诉人「取不到块了，被测代码结构变了」，
而不是让人去查一个根本不存在的「10001 缺失」。

> ⚠️ **这个对照实验我做了三轮才对**：
> 第一轮只注入违规点 → 两版都红（终点找得到，降级分支没走到）；
> 第二轮只改收尾 → 违规点离锚点太近，仍在 400 字符内，仍红；
> 第三轮**两个条件同时满足**才分离出差异。
> **教训：对照实验必须确保「破坏条件」真的走到被测分支**，否则两版都红 = 没有对照。
> 这与「注入必须自证生效」同族，但更隐蔽 —— 它不报错，只是**没有区分力**。

### 五、B 档的标注（主理人要求「写清本条只保证源码文本匹配」）

两份文件顶部已加统一声明：
> 本文件断言的是**源码文本匹配**，不保证运行时行为。
> 运行时行为由 `<对应测试文件>` 覆盖。
> 之所以仍用源码断言：部分契约（路由出参结构、RBAC 双写面同步）
> **运行时拿不到** —— 出参结构是拼装出来的，不是某个函数能返回的。
