3.3.3 为什么 singleFork 治不了也不需要治

singleFork 解决的是「多个进程并发写同名缓存」（机制 ②）， 而机制 ③ 是「测试文件在收集窗口内被创建/修改」—— 收集进程扫到了某一刻的目录快照，之后文件才落盘。 这是时序问题，不是并发写冲突问题，加串行化一点用都没有。

这不是「丢了文件」，是「快照与现实不同」： 门禁报「收集快照里没有它」，真相是「收集那一刻它还没落盘」。

3.3.4 🔴 判别法（必须先做这一步，再谈并发/状态污染）

① 跑前记磁盘文件集合 S_before，跑后记 S_after
② S_before ≠ S_after（双向差集都为空才算相等）→ 机制③ → 报 WARN
③ S_before = S_after → 才往并发写 / 状态污染 / 池配置方向查

为什么必须双向比差集：size 相同不代表集合相同——删一个加一个，总数不变但集合变了。

3.3.5 ⚠️ 最阴的地方：「多跑几次」在机制③存在时恰好会掩盖问题

磁盘稳定后连跑 6 次全绿，看起来「问题消失了」， 实际是环境不再变化了，不是门禁修好了。

「多跑几次就绿了」不能作为「原因已查明」的证据——

它只说明「现在这一刻磁盘是稳定的」。

这条直接改写了「连续跑 ≥3 次」这条判据的适用边界： 连跑 3 次是为了暴露概率性丢文件（机制 ①②）； 而机制 ③ 存在时，连跑 3 次恰好是最容易误判为「已根治」的动作。

3.3.6 与 P13 撤销的关系

P13 撤销的根因是「threads 池 native 崩溃」（机制 ③的旧名，与本节的「磁盘在变」不是同一件事——名字撞了，机制不同）。 主理人第五轮信里说「真正触发条件是机制③，判别法：先看磁盘文件数跑前跑后是否变了」—— 本节的判别法正是主理人指的那一条，我把它固化进了 P1 规格 §3.5。

3.3.7 处置

  • 门禁侧：缺文件若 mtime 在最近 N 分钟内 → 报 WARN（不是 ERROR）+ 提示「磁盘在变，请稳定后重跑」
  • 流程侧：不要在有人落盘的窗口跑门禁

⚠️ mtime 只作线索，不作判据——它绝不能成为「把 ERROR 降级成 WARN」的万能借口，

否则任何人只要 touch 一下文件就能让真事故降级。

严重级别由「磁盘是否变化」决定，mtime 只进消息文本与建议。
