# 门禁有效性审计 · 方法论可复用模板

> **类型**：方法论模板（可直接套用到任何项目）
> **作者**：顾图南（Silas Frame）｜ rnd-linban
> **日期**：2026-10
> **来源**：邻伴项目第二轮「假绿缝隙」复核（14 条线索 / 17 项复核对象 / 3 条自曝假阳性 / 1 条撤销）
> **适用**：任何有「测试 + 门禁 + 文档」三件套的团队

---

## 0. 这个模板解决什么问题

**一句话**：
> 不是查「文档对不对」「代码有没有 bug」，而是查——
> **「哪些保证看起来存在、实际不生效」。**

**为什么需要它**：
「全绿」是门禁给出的**最强信号**，也是**最常被伪造的信号**。
本项目实测到：`Test Files 1 passed` / `Tests 全部 passed` / `Errors 0` / **退出码 0** —— 而磁盘上有 2 个测试文件，**其中一个根本没跑**。

**没有报错的失败，比有报错的失败危险一个数量级。**

## 第一部分：八条核心线索（复用清单）

### 线索 1 · 门禁覆盖 vs 门禁自身在检查范围外

> **问**：这个门禁脚本本身，**会不会被类型检查 / 构建 / lint 覆盖到**？

**典型**：门禁脚本放在 `scripts/`，但 `tsconfig.json` 的 `include` 只有 `["src", "prisma"]`。
→ 门禁脚本里的类型错误**永远不会被发现**，因为没人检查它。

**检查动作**：
```bash
npx tsc -p tsconfig.json --noEmit --listFiles | grep -c scripts
# 预期 > 0；实际 0 → 门禁在检查范围外
```
**加检查**：`.ts` 与 `.mjs` 分开确认（`.mjs` 可能需要 `allowJs` 或单独的 tsconfig）。

**判据**：**门禁承载决定 CI 红绿的断言，它不被检查 = 门禁可被悄悄改坏。**
（这一条要写进 `tsconfig.json` 的注释里，让下一个人知道为什么不能删这行 include。）

### 线索 2 · 断言检查点 ≠ 破坏落点

> **问**：断言查的地方，和被破坏的地方，**是同一个数据流吗**？

**典型**：断言查 service 层的出参，但真正拼装出参的是 routes 文件。
→ 在 routes 里塞一个 `cipher` 字段，断言全绿。

**检查动作**：对每个守门测试问一句「**这个测试如果失效，最可能的原因是什么**」，然后去看那个原因是否被覆盖。

**判据**：**断言的落点与破坏落点必须在同一条数据流上。**

**正例**（本项目 `outbound-cipher-guard.test.ts:74`）：
```ts
it('整行直出必被检出（反例：证明守卫不是空断言）', ...)
```
—— 不是「断言守卫有效」，而是「**故意让守卫失效，看它会不会红**」。

**补充线索 2a · 断言的数据源形状（承钧 2026-10 裁定，宋砚秋落笔）**：

> **问**：这个断言的数据来自哪里？**换一种写法会不会静默失效？**

**数据源优先级**（越靠前越不怕格式变化）：
```
import 真实常量  >  运行时计算  >  正则扒源码
```
「正则扒源码」是**最后手段** —— 它把断言绑在了被测文件的**书写形态**上，
而书写形态是人会随手改的东西（Prettier 重排、调整嵌套层级、换引号风格）。

**但「扒源码」本身不是罪**：有些契约**只能**靠读源码验证
（如「路由文件的出参也不得带 cipher」—— 运行时拿不到出参结构）。
判据是**脆性**，不是形式。

**具体脆性清单（按危害排序）**：

| 形态 | 危害 | 症状 |
|---|---|---|
| 正则里**写死缩进量**（`/\n {8}\}/`） | 被测文件改一级缩进就失配 | 红，但**红因是「缩进变了」而非「行为错了」** → 排查方向被带偏 |
| 抠块结果 `?? ''` 兜底 + 后续断言对空串也成立 | **静默通过** | 绿，但什么也没测到（最危险） |
| 抠块结果无任何守卫（无 `toBeDefined` / 无 `throw`） | 取决于后续断言 | 可能红可能绿 |

**判据**：
- 用正则/字符串**抠块**再断言块内容 → **必须**配「匹配不到就红」的守卫
  （`expect(m?.[1]).toBeDefined()` 或 `if (!m) throw`）
- 断言**依赖格式细节**（缩进量、引号风格、闭合括号位置）→ 改用**内容/结构锚点**

**可执行化**：本项目已落 `apps/server/src/middlewares/test-assertion-source-discipline.test.ts`
（元门禁，3 条）—— 把「不得写死缩进量」与「抠块必须留守卫」变成断言，
而不是只写在文档里。**理由见 `docs/GATE-DECISIONS.md` D-003**：
写下来的纪律若没有可执行断言，下一轮就会漂。

### 线索 3 · 恒真命题

> **问**：这个断言，**换成任意垃圾输入也成立吗**？

**典型**：`prisma migrate diff --from-schema-datamodel X --to-schema-datamodel X` —— 同一个文件自比，**恒退出 0**。

**检查动作**：
```bash
# 找"同一输入自比"
grep -rn "from-schema-datamodel.*--to-schema-datamodel" scripts/
```
**更一般的判据**：
> **恒真命题 = 断言的成立与否与被检查对象的实际状态无关。**
> 识别方法：把输入改成一个明显错误的值，断言还成立吗？

**本项目已踩坑实例**（真实）：
`check-test-collection.ts` 最初直接对整份 `vitest.config.ts` 跑 `/pool:\s*'forks'/` ——
而文件头的**踩坑注释里就写着** `pool: 'forks'` 是强制项，
→ 改成 `pool: 'threads'` 后断言**照样通过**。**门禁变成恒真。**

**修法**（已落地，值得抄）：
```ts
// ① 剥掉所有注释
const cfg = stripComments(raw);
// ② 定位到 test 段内再匹配
const testBlock = cfg.slice(cfg.search(/\btest\s*:\s*\{/));
const hasForks = /pool\s*:\s*['"]forks['"]/.test(testBlock);
```
> **注释里描述配置，和配置里实际写值，在文本层面无法区分。**
> **任何"grep 配置内容"的断言，都必须先剥注释 + 定位到目标块。**

### 线索 4 · 吞异常型假通过

> **问**：错误被吞掉之后，**还有没有任何东西会红**？

**检查动作**：
```bash
grep -rnE "\.catch\(\s*\(?e\)?\s*=>\s*e\s*\)|\.catch\(\s*\(\s*\)\s*=>\s*\{\s*\}\s*\)" . --include="*.ts"
```
**⚠️ 陷阱（本项目踩过）**：这个 grep **只覆盖你指定的后缀**。
本项目第一次搜 `*.ts` 得 0 命中，写成"全量搜"；第二次搜全部 `*.ts/*.tsx` 得 **60+ 处**。
→ **搜索范围必须写进结论**：「在测试代码中未发现」≠「全仓未发现」。

**必须核的两种"更隐蔽的吞"**：
1. **错误被当成正常值**：
   ```ts
   .catch(() => [{ cnt: 0n, amt: 0n }])   // 对账查询失败 → "完美对平"
   ```
   → 比 `.catch(() => {})` 危险得多：**它让失败看起来像成功**。
2. **静默降级但无注释**：
   ```ts
   .catch(() => undefined)   // 有注释 = 有意设计；无注释 = 需追问
   ```

**判据**：
> 同样一件事，**有注释说明"为什么可以吞"** 和 **没注释**，是两种完全不同的成熟度。
> 审查时对无注释的 `.catch(() => undefined)` 逐个追问。

### 线索 5 · 守门测试被静默丢弃 ⭐（本轮最严重）

> **问**：磁盘上的每个测试文件，**都真的被执行了吗**？

**为什么这是本项目最严重的一条**：
| 现象 | 数字 | 危险度 |
|---|---|---|
| 报告 Test Files 少于磁盘 .test.ts 数 | 34/35 波动 | 高 |
| 被丢的是**整个文件** | 报告里连 failed 都不算 | — |
| `Errors 0`、**退出码 0**、全绿 | 零信号 | **极高** |
| 丢的常常正是守门测试 | 密文巡检 / RBAC / 端点契约 | **极高** |

**完整判定方法见第二部分（收集完整性断言）**—— 这条值得单独一节，因为它需要一整套机制。

### 线索 6 · mock 侧永远不报错

> **问**：mock 层和真实后端，**字段名 / 码值 / 结构一致吗**？一致这件事**有门禁吗**？

**三种不一致**（本项目全覆盖了）：
| 类型 | 具体 | 后果 |
|---|---|---|
| **码值不一致** | mock 自造 `GATE_BANNER` 等 4 个值，共享枚举里没有 | 真接后端时线下触点全部映射不上，**零报错** |
| **字段名不一致** | 服务端 `freshnessMinutes` vs 前端 `freshnessSec` | 真接后端时显示 1/60 的值，**零报错** |
| **枚举归属缺失** | 新加的 status 字段忘了登记 | 门禁自动打红（**这条已修**） |

**关键洞察**：
> **mock 与真后端的一致性，是「接后端那天」才爆发的问题——而那天往往在项目末期。**
> 必须在 mock 阶段就有机器门禁。

**做法（可复用）**：**自动发现 + 映射表 + 白名单带理由**
```
① 遍历 mock 每个集合的每个字段
② 判定「这是码值域」（全部取值符合 SCREAMING_SNAKE 形态）
③ 强制要求它要么登记到 REGISTRY（对齐某共享枚举），要么登记到 STRING_COLUMNS
④ STRING_COLUMNS 每条必须写理由，理由为空直接红
```
> 本项目 `apps/admin-web/scripts/enum-guard.ts` 是完整实现，可直接抄。
> **注意**：这个机制只管**码值域**。**出参字段名**需要另一条门禁（见第二部分 §5）。

### 线索 7 · 文档承诺 vs 磁盘

> **问**：文档说的，**磁盘上真的吗**？文档**没说的**，磁盘上有没有？

**两种方向**：
- 文档有、磁盘无 → 承诺落空
- **磁盘有、文档无** → 事实存在但没人知道，**下次有人「按文档实现」就会造出第二个**（这更隐蔽）

**⚠️ 本模板最需要强调的一条**（本项目三连踩）：
> **grep 命中一个数字 ≠ 那个数字是当前口径声明。**

**判别表**：

| 语境 | 是否当前口径 | 处理 |
|---|---|---|
| 表格首行 / 「当前为 X」/ 章节标题 | ✅ 是 | 采信 |
| 「变更记录 / v1.5 起 / 45→53」 | ❌ 历史动作 | **不采信**，去找首行 |
| 注释里引用的数字 | ❌ | 不采信 |

**六步法**：
```
① grep 拿到命中
② 读该行完整语境（前 3 行 + 后 3 行）
③ 判断这是「当前口径声明」还是「历史记录 / 注释 / 示例」
④ 若是历史记录 → 去找真正的当前口径声明处
⑤ 若找不到 → 这才是真缺口
⑥ 结论里写清楚「我核的是哪一处」
```

**同类坑（三个真实案例）**：
1. 审计者：grep `张表` 命中 `:784` 的历史记录 → 误判文档过期（**文档是对的**）
2. 审计者：grep `marketing:` 得 0 命中 → 误判成员虚报（**实际是核验时点早于落盘时点**，mtime 问题）
3. 审计者：grep `.catch` 只搜了 `*.test.ts` → 误判「全仓无吞异常」（实际 60+ 处）

**共性**：
> **grep 是「存在性」工具，不是「语义定位」工具。**
> **搜索范围 + 语境判定，两者缺一不可。**

### 线索 8 · 不可逆操作的「可逆性幻觉」

> **问**：有哪些状态机的**两条路径指向同一目标态**？准入条件一致吗？

**典型**：`canTransition(DRAFT, ACTIVE) === true`（这是 publish 的路径），
若 `resume` 也复用它 → **草稿可以绕过 publish 的全部校验**（面额范围、死券检查、库存倒挂）直接投放。

**检查动作**：枚举每个状态机的所有 `(from, to)` 对，找出**目标态相同但准入谓词不同**的那些。

**判据**：
> **终态必须真的不可逆。** `ENDED` 与 `PAUSED` 必须分开——本项目已做对。
> **同目标态的多条路径，每条都要有独立的、显式的准入校验。**

**本项目的正解（值得抄）**：
```ts
export function validateResume(snapshot: CouponSnapshot): CouponRuleResult {
  // 幂等：投放中重复 resume 不报错
  if (snapshot.status === COUPON_STATUS.ACTIVE) return { ok: true };
  if (snapshot.status !== COUPON_STATUS.PAUSED) {   // ← 显式列举，不复用 canTransition
    return { ok: false, field: 'status', code: 'STATUS_ILLEGAL', ... };
  }
  return { ok: true };
}
```
**并配一条"未知状态也拒绝"的断言**：
```ts
expect(validateResume(snap({ status: 'FUTURE_STATUS' })).ok).toBe(false);
```
—— 防新增状态未登记时被放行。

## 第二部分：收集完整性断言（可直接实现的规格）

> 详细规格见 `docs/GATE-COLLECTION-SPEC.md`。此处给出**通用骨架**。

### §1 · 为什么退出码不能当判据

**实测反例**（本项目，第三轮）：
```
--pool=forks                    → 收集 31/32/33 波动，EXIT=1
--pool=forks --no-file-parallelism → 收集 34/34/34，EXIT=0
默认池                          → 收集 28，        EXIT=1
```
**另一组实测**：退出码 1 的那次**收集反而更全**。
> **退出码与收集完整性是两个正交维度。任何只依赖 `exit code == 0` 的 CI 门禁，在本环境下都不可靠。**

### §1.1 第四轮补充：退出码与健康度的**四种组合**（最完整证据）

**同一份代码、同一个包，threads 池下连跑 12 次，观察到全部四种组合**：

| 退出码 | 收集 | `numFailedTests` | 进程 | 结论 |
|---|---|---|---|---|
| **0** | 38/38 齐 | 0 | 正常 | ✅ 真健康 |
| **1** | 38/38 齐 | **0** | 正常 | ⚠️ **退出码 1 但一切正常**，且 stdout **无任何 error 字样** |
| **139** | 38/38 齐 | 0 | **Segmentation fault** | 🔴 崩溃（128+11 = SIGSEGV） |
| **3221225477** | **无报告产出** | — | **0xC0000005 访问冲突** | 🔴 崩溃且报告未产出 |

**对照组**：配置层四件套 **14 次连跑全部落在第一行**。

> **这张表的三个结论**：
> 1. **EXIT=1 不代表有问题** —— 收集齐、零失败、无错误输出
> 2. **EXIT=0 也不代表健康** —— 同一份代码 EXIT=0 可能只是那次的运气
> 3. **崩溃的独立信号是「退出码 ≥ 128 或 Windows 异常码」** —— 这一个维度是**可信的**
>
> **实现判据**：
> ```
> 退出码 ≥ 128 或 Windows 异常码（如 3221225477）→ 一定是崩溃 → 必须 ERROR
> 退出码 0 或 1                              → 完全不可信   → 一律走四维判据
> ```
> **实现坑**：Windows 上 `execFileSync` 抛出的异常 `status` 可能是**无符号异常码**（3221225477），**不能假设 status ∈ {0,1}**，也不能假设是负数。

### §1.2 ⚠️ 「默认池」在配置了 pool 的仓库里**不成立**

> **这是我自己第三轮踩的坑，也是最容易被实现者踩的坑。**

vitest 2.1 的 CLI 默认是 `threads`（`cac.*.js:965`），**但 `vitest.config.ts` 里的 `pool` 会覆盖它**。
```ts
test: { pool: 'forks', fileParallelism: false, poolOptions: { forks: { singleFork: true } } }
```
> **「不传 pool 参数」= 配置层配置，不是 threads。**
> 要测真正的 threads 池，**必须显式 `--pool=threads`**。

**我第三轮的错误**：把「不传参数」那列标成「默认池」，据此得出「默认池有随机失败」→ **误判成「测试本身不稳定」**（判为 P13 交人排查）。
**第四轮用 `--pool=threads` 显式复现才发现**：那些失败和崩溃是 **threads 池的 native 不稳定**，配置层四件套下 **14/14 全绿**。

**判据**：
> **在断言「某个配置更稳」之前，先确认被测的那个配置真的生效了。**
> 方法：看 `testResults[].name` 集合是否等于磁盘集合 + 看 `numFailedTests`，**不要靠命令行标签**。

### §1.3 四种「文件变少」的机制（修法完全不同，判据也完全不同）

| 形态 | 判据 | 根因 | 修法 |
|---|---|---|---|
| **机制 1** EPERM 写盘 | 清缓存后**仍不收集** | 沙箱 broker IPC 裁决 | `cacheDir` 指向项目内 / 换池 |
| **机制 2** 并发写同名缓存 | 清缓存后**恢复** | 并发写缓存目录 | `fileParallelism: false` / `singleFork` |
| **机制 3** native 崩溃 | **退出码 ≥ 128 或 Windows 异常码**，可能无报告 | threads 池 native 段错误 | 换池（forks） |

> **把机制 3 误判成机制 1，就会去改 `cacheDir` / `TMPDIR` —— 改了半天，根因根本不在那里。**
> 这就是「机制必须分清」的代价。

#### §1.3.1 第四种机制：磁盘在变（**第五轮新增，最容易被误判的一种**）

**现象**：门禁报「缺 X.test.ts」，但该文件**确实在磁盘上**，
且集合级比对显示**差集唯一、无顶替者**（不是「A 丢了 B 补上」）。

**证据链**（主理人 2026-10-22 实测）：
```
06:20:20  落盘 coupon-state-machine.test.ts
06:20:38  再落盘另一个测试文件
   ↓ 同期跑门禁 → 报缺 coupon-state-machine.test.ts
   ↓ 磁盘稳定后 → 连跑 6 次门禁 + 6 次 vitest → 全 38/38，零波动
```

**为什么 `singleFork` 治不了也不需要治**：
`singleFork` 解决「**多进程**并发写同名缓存」，而这一种是「**测试文件在收集窗口内被创建/修改**」——
收集进程扫到了某一刻的目录快照，之后文件才落盘。
**这是时序问题，不是并发写冲突问题**，加串行化一点用都没有。

**这不是「丢了文件」，是「快照与现实不同」**：
门禁报「收集快照里没有它」，真相是「收集那一刻它还没落盘」。

**🔴 判别法（必须先做这一步，再谈并发/状态污染）**：
```
① 跑前记磁盘文件集合 S_before，跑后记 S_after
② S_before ≠ S_after（**双向差集都为空**才算相等）→ 机制③ → WARN
③ S_before = S_after → 才往并发写 / 状态污染 / 池配置方向查
```

**⚠️ 最阴的地方：「多跑几次」在机制③存在时恰好会掩盖问题**——
磁盘稳定后连跑 6 次全绿，看起来「问题消失了」，
实际是**环境不再变化**了，不是门禁修好了。
**「多跑几次就绿了」不能作为「原因已查明」的证据**，它只说明「现在这一刻磁盘是稳定的」。

**处置**：
- 门禁侧：缺的文件若 mtime 在「最近 N 分钟内」→ 报 **WARN**（不是 ERROR）+ 提示「磁盘在变，请稳定后重跑」
- 流程侧：**不要**在有人落盘的窗口跑门禁

### §1.4 「测试失败」≠「环境失败」—— 两者现象几乎一样

| 来源 | 特征 | 归属 |
|---|---|---|
| **测试失败** | `assertionResults[].status === 'failed'`，有 `failureMessages`（`expected X to be Y`） | 业务代码 |
| **环境失败** | 退出码 ≥ 128 / 报告缺失 / 收集数波动 | 工具链 |

**区分方法**（按成本从低到高）：
1. 看 `failureMessages` 是不是**断言消息**
2. 看**退出码**（≥128 = 崩溃）
3. 看**收集集合**
4. **在两个不同池下各跑一次** —— 只在某一个池下失败 → 环境问题

> **第 4 条最省事，但要求能切换配置** → 所以 `pool` 必须是**配置层固化**的：
> **只有配置固定，才能做「A/B 对照」来区分环境与代码。**

### §1.5 「`node --check` 通过」≠「代码被执行了」（第四轮补，最隐蔽的一类）

**事故原委**（主理人亲历）：写 `scripts/verify-all.cjs` 时文件头 `/**` 忘闭合 `*/`，
一路吞到 72 行，把三行 `const` 声明全吞进注释 → 顶层变量全 `undefined` →
**`node --check` 通过**（被吞代码语法上完全合法）→ **但代码根本没执行**。

**为什么静态检查查不出**：注释未闭合是「**语法合法但语义丢失**」的一类故障。
被吞的代码从语言视角看根本不存在，所以它既不违反语法，也不产生任何告警。

| 手段 | 能查到什么 | 查不到什么 |
|---|---|---|
| `node --check` | 语法错误 | **注释未闭合吞代码**、变量未声明、逻辑错 |
| `tsc --noEmit` | 类型错误 + 未使用变量 | 运行时才暴露的路径 |
| **跑一次并看输出** | **「这段代码到底执行了没有」** | — |

**可靠判据是「跑一次并看输出」，不是「静态检查通过」。**

**🔴 对审计报告的直接约束（这条最要紧）**：
> 写「已验证」「未发现问题」时，**验证手段本身可能失效而它看起来有效**。
> 所以每条「已验证」都必须能回答：**① 我跑的是什么命令？② 输出是什么？**
> （具体到参数与工作目录，不是「通过了」三个字）

**为什么这对门禁审计特别致命**：门禁审计的全部价值建立在「门禁真的会红」这个假设上。
若门禁脚本因一个未闭合注释而**从未真正执行过断言**，那么它一直报「全绿」、
退出码是 0、CI 一直是绿的——**而它一个断言都没跑过**。
这是「**门禁在检查范围外**」（线索 1）最隐蔽的一种形态：
**门禁文件存在、可运行、退出码正确**。

**最便宜的存活判据**：要求门禁脚本**至少打印一行自己的结论**
（如「检查了 N 个包，ERROR 0，WARN 2」），聚合入口据此判断「它真的跑过了」。
**「没有输出」=「没跑」**。

**同源三故障**（主理人已写入 `D:/wiki/Learning/insight-assert-right-display-wrong-2026-10-22.md`）：
1. **断言对、显示错**（→ 第五维）
2. **注释未闭合吞代码**（→ 本条）
3. **两态当三态**（→ §7 三态自证）

**三条的共同结构**：
> **「看起来对」与「实际上对」之间没有可见的差别**——
> 所以必须有一层**主动去制造可见差别**的机制（自证 / 显示层同源 / 三态区分），
> 而不能靠「读起来没问题」。

### §1.6 「上下文性质」判别法（grep 命中 ≠ 事实所在处 的姐妹条）

**第四轮我自己踩的坑**：我用 grep 查 `DATABASE.md` 里的表数，
命中 `docs/DATABASE.md:784` 的「45→53」**历史变更记录**，
于是报了「文档说 54 表、实测 54 表，但文档别处写 45」——**假阳性**。
主理人纠正后我撤销了那条（P4）。

**根因**：grep 是「**存在性**」工具，不是「**语义定位**」工具。
命中一行只说明「这行文字里出现了这个数字」，不说明「这行是**当前口径声明**」。

**六步法**：
1. grep 命中 → 2. 读该行**完整语境**（前 3 后 3）→ 3. 判断这段的**性质**：
   是「当前口径声明」还是「历史记录 / 注释 / 示例 / 变更日志」？
4. 若是历史 → **去找真正的当前口径**（通常在文档开头的概览表或章节首句）
5. 找不到才是真缺口 → 6. 结论里**写清核的是哪一处**（行号 + 性质）

**§1.6 判别法（第五轮定稿，比六步法更快）**：
> **读命中行上下各 5 行，看这段的性质是「事实」还是「变更记录/历史沿革」。**
> 5 行不够就往上翻到最近的标题——**标题是性质的判据**：
> 在「变更记录」「历史」「附录」「修订历史」标题下的数字，一律不是当前口径。

**报告层的三段式写法**（与「未发现问题」三段式同源）：
> 「我核的是 `docs/DATABASE.md:6` 的**概览声明**（当前口径），
> 不是 `:784` 的**变更记录**（历史）」

**为什么这条值得单列**：它是**唯一一条会让我自己产生假阳性**的线索。
其余 7 条线索查的是「门禁有没有效」，这条查的是「**我自己的核验**有没有效」——
而审计报告的可信度全靠后者。

### §2 · 关键陷阱：`numTotalTestSuites` 不是文件数

```
numTotalTestSuites = 195   ← describe 块数 ❌
testResults.length  = 35    ← 文件数 ✅
numTotalTests      = 737   ← 用例数
```
> **任何「A === B === C」的三数比对，必须先确认每个数的语义。**
> 用错了不会假绿，会**假红**——但更糟的是有人会去"修"那个假的红。


### §3 · 五维判据（第五维 = 显示层自身正确性）

| # | 维度 | 判据 | 抓什么 |
|---|---|---|---|
| ① | **集合相等** | `expectedFiles`（磁盘 find）**集合** === `actualFiles`（reporter 列出），**不是数量相等** | 数量守恒的丢（丢 A 收 B） |
| ② | **实际执行集合相等** | reporter 报的文件 === **实际产生了执行记录**的文件（看 `status`，`pending`/`skipped` 不算执行） | 「被报告」≠「被执行」 |
| ③ | **正交第二判据** | `numFailedTests === 0` 且 `numPendingTests === 0`，**独立**成立 | 通过「零失败」反证无收集阶段失败，**不依赖退出码** |
| ④ | **禁列清单（带理由）** | 允许排除某些文件，但**每条必须写理由** | 防「为了让门禁变绿而删文件」 |

**① 为什么要集合而非数量**：
> 具体构造：磁盘新增 1 个测试文件的同时，某个旧文件因 EPERM 被丢
> → `collected.length === diskFiles.length` **成立**，但**新文件没跑、旧守门测试没跑**，门禁全绿。

**① 的输出要求**：
> **必须逐个文件名打印漏掉的测试。**
> 「31 ≠ 34」没有可操作性；「漏掉 `outbound-cipher-guard.test.ts`（守门：密文出参守卫）」才可操作。

**④ 禁列的语义（必须写进文档和代码注释）**：
> **禁列 = 「这个文件一旦消失，说明门禁本身失效」，不是「这个文件可以删」。**
> 理由字段为空 = 免检牌 = 下一个文件可以随便进来。

#### §3.5 第五维：显示层自身正确性（**显示层必须与断言层同源**）

**来源**：一次真实自相矛盾（主理人实测撞到）——
门禁同一行输出「磁盘A=38 / 收集B=0 / 通过C=38」。

**根因**：`r.collected` 从未赋值（初始化为 0），断言用的是**局部** `collected.length`（对），
显示行印的是 `r.collected`（永远 0）。

```ts
// ❌ 违规：断言层与显示层取自两个不同的源
const collected = testResults.map(r => r.name);
if (collected.length !== diskFiles.length) { /* 断言用 collected ✅ */ }
render(`收集B=${r.collected}`);          // 显示用 r.collected ❌（永远是 0）

// ✅ 合规：断言与显示共用同一份数据源
const collected = testResults.map(r => r.name);
r.collected = collected.length;
if (collected.length !== diskFiles.length) { /* 断言 ✅ */ }
render(`收集B=${r.collected}`);          // 显示 ✅（同一个值）
```

**更严的写法**：显示层直接读断言层算出的局部变量，**不读任何中间字段**：
```ts
const A = diskFiles.length, B = collected.length, C = passedFiles;
render(`磁盘A=${A} / 收集B=${B} / 通过C=${C}`);
```

**为什么这一维独立存在**：前四维保证「判定是对的」，第五维保证「**判定结果被如实显示**」。
两者是不同的失效面：**「断言对、显示错」比「断言错」更危险**——
因为断言错会让人去修，显示错会让人**不修**（看到「A=38」以为没事，看到「B=0」以为全崩，两种都是误判）。

**自检方法**：故意让 `r.collected` 少赋一次值 → 输出的 A/B/C 必须**立刻自相矛盾**
→ 说明断言层与显示层不是同一个源；恢复后三数必须一致。

**判据一句话**：**显示的每一个数字，都必须能追溯到断言用的那个变量。**

#### §3.6 维度④ 禁列必须带「理由 + 处置」两栏

```
禁列：<断言名> | 理由：<为什么测不到> | 若真发生：<去哪查 / 谁能发现>
```

**为什么只写理由不够**（第五轮主理人补的硬要求）：
只写「理由」不写「去处」，人看到禁列只会**跳过**（「这文件测不到，算了」），
而不会去补。**理由解释了「为什么可以不测」，处置栏才回答「那出事时谁会发现」。**
没有处置栏的禁列 = 免检牌 = 一个永久的、无人认领的盲区。

### §4 · 守门测试点名：清单必须能防腐

**问题**：手写清单会腐烂。**新增的守门测试默认不在清单里** → 它被丢时门禁不会红。

**解法：派生 + 手写，双清单**
```
M（派生，永不腐烂）：命名约定推导，如
    /-guard\.test\.ts$/  /contract\.test\.ts$/  /-wiring\.test\.ts$/  /\.gates\.test\.ts$/
G（手写，带 guards 理由）：契约没约定但关键的

断言：M ∪ G ⊆ execSet   且   M ∪ G ≠ ∅
```
> **`M ∪ G ≠ ∅` 这条不能省** —— 否则派生正则失效时清单变空，断言恒真。

**手写清单 G 每条必须带 `guards` 字段**（守护什么）：理由是人读的，也是交接文档。

### §5 · 出参字段三方对账（mock ↔ 服务端 ↔ 前端）

> 这是线索 6 的延伸，也是**最高性价比的一条**——本项目实测出 17 个字段名不对齐。

```
契约字段表（若缺 → 补，这是根因）
      ⊆ 服务端出参
      ⊆ 前端消费类型
```
**做法**：
1. **契约必须给字段级出参表**（字段名 + 类型 + 单位 + 必填性）。散文描述不算。
2. 以**服务端**为事实源，前端类型从契约生成或从 shared 导入
3. **门禁做集合对账**，不是数量对账

**实测反例（字段名 + 单位双错）**：
```
服务端：freshnessMinutes   ← 分钟
前端：  freshnessSec        ← 秒，且前端自己 /60 当分钟用
→ 真后端一接：显示实际值的 1/60，且 undefined 时显示 NaN，零报错
```

**判据**：
> **"入表了"不等于"能用"。完整链条**：
> `入表 → 有出口 → 读得对（消费方理解一致）→ 读得全（没有漏字段）`
> **很多"已完成"只走到第一步。**

### §6 · 「只增不减」基线

**问题**：硬编码期望值（`assert collected === 34`）在协作下**必然腐烂**——
有人加了第 35 个文件 → 门禁红了 → 他去改断言 → 改成了 35。**整个过程没人再确认 35 是不是对的。**

**更隐蔽的问题**：**基线在测试过程中会漂移**。
本项目实测：脚本启动时磁盘 34 个，跑到一半队友新增 1 个变成 35。

**做法**：
```
基线文件：<pkg>/.tmp/collection-baseline.json   （不入版本库）
规则：
  本次收集 < 基线  → ERROR（说明有文件被丢）
  本次收集 > 基线  → 自动更新基线 + INFO（有人加了新测试，正常）
  数量 == 但集合不同 → ERROR（有人换文件，或丢了又多了）
```
> 基线**不硬编码数字**，而是**集合的并集历史**。
> 判定永远基于「集合是否 ⊆ 基线 ∪ 本次」。

### §7 · 三态自证（证明门禁有牙齿）

**目的**：证明这条门禁**不是恒真**。

```
① 记录打破前：收集数 B_before，各守门测试结果
② 故意打破
③ 重跑 → 观察
④ 撤销 → 重跑 → 观察
```

**三态断言（缺一不可）**：
```
打破后必须同时满足：
  ① 收集数 === 打破前收集数          （文件没被丢）
  AND 出现明确的「断言失败」信息        （不是「解析错误」/ 不是「未收集」）
  AND 恢复后：收集数回到原值 + 全绿
```

**为什么 ① 不可省（主理人补的关键一条）**：
如果「打破」动作本身让文件**无法被收集**（比如加了行 `import x from 'nonexistent'` 导致解析失败）：
- vitest 在**收集阶段**就报错
- 根本进不到断言阶段
- 你看到的「红」是**解析错误**，不是**断言失败**

> **三种解释，同一个现象「红」**：
> ① 断言没牙齿 ② 破坏没生效 ③ **破坏导致文件无法收集**
> 必须用 ① + ② 联合区分。

**推荐打破手法**：
- ✅ 改断言期望值：`expect(x).toBe(1)` → `expect(x).toBe(999)`
- ✅ 加一条必然失败的断言：`expect(true).toBe(false)`
- ❌ 引入语法错误 / 不存在的 import（会走解析失败路径）

**自证记录必须落盘**（不能口头说"验证过"）：
```
docs/gate-selfproof/P1-<日期>.md
- 打破的断言位置：src/xxx.test.ts:123
- 打破前：B=35，断言通过
- 打破后：B=35，报 "AssertionError: expected 1 to be 999"（非解析错误）
- 恢复后：B=35，全绿
```

> **反例（值得抄）**：本项目 `check-collection.mjs:138` 有一条断言
> 「上一轮自证记录已清空（避免『历史上跑过就行』的累积假绿）」。
> **自证记录永久累积，会让后来者以为"一直验过"** —— 这是个很好的设计。

### §8 · 归因表：对→错 必须阻塞

| 变化 | 归因 | 动作 |
|---|---|---|
| 错 → 对 | 修复生效 | **接受** |
| 对 → 错 | **修复引入了新的丢失路径** | **阻塞，立即调查** |

> **「对→错」比「错→对」更重要** —— 它意味着**给出的方案本身有害**。

**实现**：
```
基线 C_prev，本轮 C_now，应收集集合 A：
  C_prev ⊆ C_now 且 C_now 仍 ⊊ A  → 「对→错」 → ERROR（阻塞）
  C_prev ⊄ C_now 且 C_now 仍 ⊊ A  → 「错→对（部分）」 → ERROR（继续修）
  C_now === A 且 C_prev ≠ C_now    → 「错→对」 → 接受
```
> 只有 `C_now === A` 才算真修好了 —— 靠删文件修的会让 `C_now ⊂ A`，被维度 ① 拦下。

### §9 · 连续跑 ≥3 次

```
3 次全部满足「集合 == 磁盘集合」 → 通过
任意一次缺失 → 失败，且必须打印那一次的缺失文件名
```
> **不得用「3 次里 2 次通过」的多数决** —— 丢文件是概率事件，多数决会放过 1/3 的丢失率。

**成本折中**：
```
本地/CI 门禁：跑 1 次（快速反馈）+ 跨次基线比对
夜间/发布前：跑 3 次（随机性只能靠重复暴露）
```
> 关键是**跨次有基线可比**，而不是每次都跑 3 遍。

## 第三部分：报告怎么写才不被误采信

### §10 · 「未发现问题」的三段式

```
✅ 本轮在 <具体维度> 未发现实例。
   证据：<可复现命令 + 实际输出>
   不覆盖：① <具体盲区> ② <具体盲区> ③ <具体盲区>
```

**反例**：
```
❌ 「吞异常型假通过 —— 不存在」
```
**问题**：
1. 「不存在」= 断言这个维度没问题，但实际只能说"没查到"
2. 没有证据链
3. 没有边界，下一个人会以为这个维度已经被穷尽了

**「不覆盖」要具体到可验证**：
```
✅ 不覆盖：① 生产代码的 60+ 处 .catch()（已核 8 处关键路径）
           ② Promise 链中间层的 await 缺失
           ③ 跨进程/跨服务的错误传播
❌ 不覆盖：其他情况
```

### §11 · 主动自曝假阳性（本模板最专业的部分）

**规则**：
> **报告里每一个"未发现问题"，都要标出它的证据强度和可能失效的条件。**
> **发现了自己的假阳性，要写在报告正文，不要藏。**

**本项目自曝 3 个假阳性**：
| # | 我原来的结论 | 实际情况 | 根因 |
|---|---|---|---|
| 1 | 「文档表数 53/64 已过期」 | **文档是对的**（54/66），我命中的是历史变更记录 | grep 命中 ≠ 当前口径 |
| 2 | 「全量搜 catch，0 命中」 | 全仓 **60+ 处**，我只搜了测试文件 | 搜索范围 ≠ 声称范围 |
| 3 | 「券 `resume` 防御在 `modules/marketing/coupon.ts`」 | 实际在 `domain/coupon.ts` | 引用路径未复核 |

> **自曝假阳性不削弱报告，反而是报告最可信的部分。**
> 它示范了「我这条结论的证据链有多强」——而这正是读者最需要知道的。

### §12 · 复核别人报的东西

> **不要采信任何人的自述（包括发起人的）。**

**清单**：
```
① 自己到磁盘核，不用对方给的行号（行号会因并发编辑失效）
② 核到的结论若与对方不同 → 先怀疑自己，再质疑对方
③ 对方的"已修"要核**当前磁盘状态**，不核"他说改了"
④ 对方说"测过了"→ 核**测试文件在不在收集清单里**（见 §13）
```

### §13 · 「已核过」≠「真跑过」⭐

**主理人的怀疑**：「有些成员报的『已核过』其实是在一个没真正运行的测试上做的。」

**这是真的，而且概率不低。** 原因：
- 守门测试**被静默丢弃**（线索 5）→ 报告全绿 → 没人发现它没跑
- 报告里写"✅ 通过"的人**看的是 CI 输出**，不是"这个文件到底跑没跑"

**必做的两个检查**：

**① 点名核对**：把对方声称"已核过"的项目，映射到**具体测试文件**，再核这些文件**在不在执行清单里**。

**② 单跑 vs 全跑对比**（捕捉「单跑红、全跑绿」）：
```
全量跑 → 记录结果
单跑该测试 → 记录结果
两者不一致 → 存在跨测试状态依赖
```
**为什么要做**：有些测试的断言依赖了**别的测试留下的状态**（`beforeAll` 建立的数据、全局 mock 缓存、模块单例污染）。
全量跑时前面的测试恰好把它"喂"饱了，单跑就红。

> **⚠️ 这个检测必须进 CI，不能靠人工。**
> 人工单跑和 CI 全跑的环境不同，人工单跑会跳过 `beforeAll`，反而"更干净"，可能掩盖问题。

**本项目实测**：12 个守门测试逐个单跑 → **12/12 全绿，与全量一致 → 未发现实例**。
**不覆盖**：依赖跨文件 `beforeAll` 的顺序依赖 / 全局单例污染。

## 第四部分：可直接复制的检查清单

### A · 机制静默失效
```
[ ] 每个测试文件都真的被执行？（集合相等，非仅数量）
[ ] 漏掉的文件是否逐个文件名打印？
[ ] 关键守门测试在清单里？清单是手写还是从命名约定派生？
[ ] 守门脚本在 tsc/构建的 include 范围内？（.ts 与 .mjs 分开确认）
[ ] 聚合入口存在吗？CI 只调它，还是让人记得逐个跑？
[ ] 池配置（pool/threads/forks/singleFork）固化在配置文件里，还是靠命令行传？
[ ] 退出码被当成判据了吗？（不该）
[ ] numTotalTestSuites 被当成文件数了吗？（不该）
[ ] 出参字段三方（契约/服务端/前端）对账了吗？
```

### B · 恒真命题
```
[ ] 有「同一输入自比」的断言吗？
[ ] grep 配置内容的断言，剥注释 + 定位到目标块了吗？
[ ] 把被检查对象换成任意垃圾值，断言还成立吗？
[ ] 断言查的字段 == 被破坏的字段吗？
[ ] 断言的落点与破坏落点在同一条数据流上吗？
[ ] 派生清单（M ∪ G）会不会为空？为空时断言还成立吗？
```

### C · 吞异常
```
[ ] 有 .catch(e=>e) / .catch(()=>{}) 后仍 expect(true) 吗？
[ ] 有 .catch(() => 正常值) 吗？（比 .catch(()=>{}) 更危险）
[ ] 无注释的 .catch(()=>undefined) 逐个追问过吗？
[ ] try { 目标(); expect.unreachable() } catch { 断言 } 范式用对了吗？
[ ] 错误被吞后，退出码与输出还能暴露失败吗？
[ ] 你的 grep 范围 == 你声称的范围吗？
```

### D · 不可逆性幻觉
```
[ ] 有哪些状态机的两条路径指向同一目标态？准入条件一致吗？
[ ] 「已投放/已发布/已生效」能否被绕过校验直接到达？
[ ] 终态是否真的不可逆？
[ ] 未知/新登记状态是否被明确拒绝？
```

### E · 文档与磁盘
```
[ ] 文档声明的表数/枚举数/码数与磁盘一致吗？
[ ] 文档说的"刻意未落"的东西，现在落了吗？
[ ] mock 的字段名有自动交叉断言吗？（号段镜像管不到字段名）
[ ] grep 命中的数字，是当前口径还是历史记录？
[ ] mock 与真后端的字段名/单位一致吗？
```

### F · 报告自审
```
[ ] 每个「未发现问题」都写成了「本轮在 N 个维度未发现实例」？
[ ] 每条都附了「不覆盖」清单，且清单具体到可验证？
[ ] 自己的假阳性写进正文了吗？
[ ] 对方的「已核过」都映射到具体测试文件，且核过它在收集清单里？
[ ] 每个守门测试都做过单跑 vs 全跑对比吗？
```

## 第五部分：一句话总结

> **门禁的价值不在于"跑通了"，而在于"跑不通时一定会红"。**
>
> **任何一条保证，都要问三遍**：
> ① 它**真的在跑**吗？（不是"看起来在跑"）
> ② 它**跑全了**吗？（不是"跑了一部分"）
> ③ 它**跑的时候失败了会红**吗？（不是"恒真"）
>
> **三遍都过了，这道门才是门；少一遍，它就是一张发免检牌的纸。**
