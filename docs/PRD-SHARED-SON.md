## 1. 为什么做这个

战略文档的「四位一体」供给模型里，**共享儿子**（文档中称「共享孙辈」）是唯一同时满足三个条件的角色：

1. **有真实货币流** —— 按时薪付费，可直接进现有分账链路（另外两位角色没有）
2. **支付意愿已被验证** —— 战略分析：中国老人对非医疗陪伴付费意愿低，但「陪诊/代跑腿/教手机」这类**辅助性服务**付费意愿高
3. **供给端可持续** —— 大学生/年轻职场人群，弹性就业、单次服务时长短、供需两端都在移动端

> **本轮只开放共享儿子**。时间银行（积分兑换）与社区志愿者（荣誉补贴）**没有真实货币流**，
> 接入时**绝不能污染分账流水**——这是 §4 结算隔离的硬要求。

## 2. 用户故事

| 角色 | 故事 | 验收 |
|---|---|---|
| **子女**（代下单为主） | 我工作忙，老爸一个人在广州。我想要个**社区里的年轻后辈**陪他聊聊天、教他用智能手机，周末陪他逛逛公园。 | 下单时可指定「共享儿子」；匹配到的陪聊员卡片显示该角色 |
| **老人**（直用） | 我不太会用手机，让子女帮我约人就行。 | 老人直用路径**不出现角色选择步骤**，默认共享儿子 |
| **共享儿子**（供给） | 我是大学生，时间灵活，想赚点外快，也擅长教人用手机。 | 入驻时选择「共享儿子」角色；按小时计酬；双向评价 |
| **平台运营** | 我要看清楚现在供给侧都什么人，分别多少单。 | 后台陪聊员列表可按角色筛选；审核台可见申请人角色 |

## 3. 产品口径（**文案纪律，不可违背**）

### 3.1 人设

共享儿子 = **社区里的年轻后辈**，大学生/刚工作的年轻人，用陪伴力和一点技术能力，帮社区老人解决「没人陪、不会用手机、腿脚不便出门」这三件事。

### 3.2 话术红线

| ✅ 正确 | ❌ 禁止 |
|---|---|
| 辅助子女（帮子女尽一份心） | 替代子女 / 像儿子一样伺候 |
| 陪聊、教手机、陪逛、代跑腿 | 护理 / 照护 / 喂食 / 洗澡 |
| 社区里的年轻后辈 | 护工 / 保姆 / 孝子贤孙 |
| 按时陪伴、按小时计酬 | 专业护理 / 医疗陪护 |

> 依据：战略文档 §1.5 中美差异分析——中国孝道文化下，「花钱找人陪 = 不孝」是真实阻力，
> 因此产品话术必须是「**辅助子女**」，而非「替代子女」。
> 「护理/照护」类词汇属于「专业陪护」角色，本轮不开，**提前用词会造成预期错位**。

### 3.3 适老化约束（用户端最硬的要求）

用户端是老人直用的小程序：

- **大字 / 语音优先 / 极简流程**，样式尺度**照抄现有页面**，不自创一套
- 角色选择主要发生在**子女代下单**路径；**老人直用路径不得新增任何操作步骤**
- 新增文案一律短句、无生僻词、避免专业术语

---

## 4. 结算隔离（硬要求）

四种角色的付费方式完全不同：

| 角色 | 结算方式 | 是否进分账流水 |
|---|---|---|
| **共享儿子** | 时薪付费 | ✅ 进 |
| 时间银行 | 积分兑换（未来） | ❌ **绝不进** |
| 社区志愿者 | 荣誉 + 补贴 | ❌ **绝不进** |
| 专业陪护 | 高客单付费 | ✅ 进 |

> 依据：架构 §13 健康活动感知模块已有「账务隔离」裁定（订阅收入不进 `profit_sharing_records`、
> 不参与抽成、财务对账分开）。非货币结算模式必须沿用同一纪律。
> 本轮**只实现共享儿子（进分账）**，但代码结构须留好隔离位——具体见 ARCHITECTURE.md §15。

## 5. 本轮范围

### ✅ 做

| 项 | 说明 |
|---|---|
| 角色建模 | `companion_role` 枚举，四值留位，**本轮仅 `SHARED_SON` 开放** |
| 陪聊员端入驻选角色 | 角色卡片选择，提交 `companionRole` |
| 用户端展示与指定 | 陪聊员卡片显示角色；需求可指定角色（仅一个可选项） |
| 后台管理维度 | 陪聊员列表角色列 + 筛选；审核台可见申请人角色 |
| 派单打分 | 老人指定角色时，同等条件下该角色优先 |
| 入驻校验 | 服务端只接受 `SHARED_SON`，其余值明确拒绝（非静默接受） |
| 结算隔离留位 | 角色 → 结算模式 → 是否进分账流水的映射与单测 |

### ❌ 不做（超出本轮）

- 时间银行 / 社区志愿者 / 专业陪护的**实际功能**（枚举留位，UI 上不可创建）
- 积分账本、荣誉补贴发放
- 共享儿子的**专属服务类型**（本轮仍复用 `CHAT`；`ACCOMPANY` 仍标注「预留，MVP 不开放」）
- 角色化审核的完整分岔逻辑（本轮先做展示与筛选，差异待 ARCHITECTURE.md §15 定稿后补）

## 6. 验收标准

| # | 标准 | 怎么验 |
|---|---|---|
| 1 | 枚举镜像一致 | schema ↔ `packages/shared/src/enums.ts` 逐字一致，enum-mirror 门禁绿 |
| 2 | 门禁登记完整 | `enum-guard.ts` 已登记 `companions.role`；理由非空 |
| 3 | 派单打分生效 | 角色维度有单测；**既有 `dispatch.test.ts` 一个都不能挂** |
| 4 | 服务端拒绝非法角色 | 提交 `TIME_BANK` 等预留值返回明确错误码 |
| 5 | 结算隔离 | 单测断言：非货币结算模式**不出现在分账流水判定中** |
| 6 | 老人路径零增步 | 老人直用流程的步骤数与改造前一致 |
| 7 | 文案合规 | 全量文案抽查无「护理/照护/替代子女」等禁用词 |
| 8 | 门禁全绿 | `npm run verify:all` 通过 |
