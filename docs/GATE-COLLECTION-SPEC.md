## 0. 一句话

> **「测试跑过了」不是可观测事实，「哪些文件被执行了」才是。**
> 门禁要断言的是**文件集合**，不是数量、不是退出码、不是「Tests 737 passed」。

## 1. 为什么需要这条（本项目已真实踩到）

| 现象 | 数字 | 危险度 |
|---|---|---|
| server 默认池 | 34/35 波动，Tests 全过 | 高 |

**最恶劣的一点**：`Errors 0`、退出码 `0`、报告全绿。**没有任何信号表明出事了。**

### 2.1 ⚠️ 第四轮补充：「默认池」这个说法在配置了 pool 的仓库里**不成立**

> 这是规格里最容易被实现者踩的一个坑，也是我第三轮自己踩的。

**事实**：vitest 2.1 的 CLI 默认是 `threads`（`node_modules/vitest/dist/chunks/cac.*.js:965`：「default: `threads`」），**但 `vitest.config.ts` 里的 `pool` 会覆盖它**。

```ts
// apps/server/vitest.config.ts（剥注释后）
test: {
  pool: 'forks',                        // ← 这一行让"默认池"不再是 threads
  fileParallelism: false,
  poolOptions: { forks: { singleFork: true } },
  cacheDir: '.../node_modules/.vitest',
}
```

> **所以「不传 pool 参数」= 配置层的四件套，不是 threads。**
> 要测真正的 threads 池，**必须显式 `--pool=threads`**。

**这条为什么重要**：我在第三轮报告里把「不传参数」的那一列标成「默认池」，据此得出「默认池有随机失败」→ 误判成「测试本身不稳定」（P13）。第四轮用 `--pool=threads` 显式复现才发现**那批失败和崩溃是 threads 池的 native 不稳定**。

**给实现者的判据**：
> **在断言「某个配置更稳」之前，先确认被测的那个配置真的生效了。**
> 最可靠的办法：**看 JSON reporter 里 `testResults[].name` 的集合是否等于磁盘集合**（收集维度）+ **看 `numFailedTests`**（执行维度），**不要靠命令行标签**。

### 2.2 `numTotalTestSuites` 不是文件数（最关键的坑）

```
numTotalTestSuites = 195   ← describe 块数（737 个 it 分组后的块数）❌
testResults.length  = 35    ← 真正的文件数 ✅
numTotalTests      = 737   ← 真正的用例数
```

**验证方式**：737 个 `assertionResults` **全部**带 `ancestorTitles`（即全部位于 describe 内）→ 195 是分组块数。

**这是规格里最关键的一个坑**：主理人最初给的「三数比对 `A === B === C`，B 取 `numTotalTestSuites`」**按字面实现会直接假红**（35 ≠ 195）。
> **文件数必须取 `testResults.length`，不能取 `numTotalTestSuites`。**
> `numTotalTestSuites` 是 describe 块数，`numTotalTests` 是用例数，两者都不是文件数。

### 2.3 退出码与健康度的四种组合（第四轮实测）

**在 threads 池下连跑 12 次，观察到全部四种组合**：

| 退出码 | 收集 | `numFailedTests` | 进程 | 结论 |
|---|---|---|---|---|
| **0** | 38/38 齐 | 0 | 正常 | ✅ 真健康 |
| **1** | 38/38 齐 | **0** | 正常 | ⚠️ **退出码 1 但一切正常** —— 退出码不可信的最强版本 |
| **139** | 38/38 齐 | 0 | **Segmentation fault** | 🔴 崩溃（128+11 = SIGSEGV） |
| **3221225477** | **0/35（无报告）** | — | **0xC0000005 访问冲突** | 🔴 崩溃且报告未产出 |

**对照组**：配置层四件套 **14 次连跑（8+6）全部落在第一行**（EXIT=0 / 38 齐 / 0 失败 / 无崩溃）。

> **这张表是「退出码不可信」最完整的证据**：
> - **EXIT=1 不代表有问题**（第二行）
> - **EXIT=0 也不代表健康**（第二行反证：同样的 EXIT=0 可能是巧合）
> - **崩溃的特征是退出码 ≥ 128 或 Windows 异常码** —— 这是一个**独立的、极强的信号**
>
> **给实现者的判据**：
> ```
> 退出码 ≥ 128  → 一定是信号（SIGSEGV/SIGABRT…）  → 必须 ERROR
> 退出码 0 或 1 → 完全不可信                     → 一律走四维判据
> ```
> **实现注意**：Windows 上 `execFileSync` 抛出的异常对象里，`status` 可能是 `3221225477` 这类**无符号异常码**。**不能假设 status ∈ {0,1}**，也不能假设它是负数（POSIX 信号）。

### 2.4 四种「文件变少」的机制分类（第五轮补全第四种）

| 形态 | 现象 | 判据 | 根因 |
|---|---|---|---|
| **机制 1** EPERM 写盘 | 文件数少，报告说 passed，退出码 0/1 | 清缓存后**仍不收集** | 沙箱 broker IPC 裁决 `fs/promises.writeFile` |
| **机制 2** 并发写同名缓存 | 同上 | 清缓存后**恢复** | 并发写缓存目录互相覆盖 |
| **机制 3** native 崩溃 | 文件数少，**退出码 139 / 0xC0000005**，可能**无报告** | 退出码是**信号值或 Windows 异常码** | threads 池 native 段错误 |

> **机制 3 的关键特征**：崩在**执行阶段**，所以 `testResults` 里仍可能有全部文件（38/38），但**测试数不完整**；也可能崩在写报告前 → **报告根本没产出**。
> **主理人观测到的「31/32/33 波动」真身就是机制 3** —— 不是丢了文件，是崩了之后剩下的没跑完。

**为什么必须区分三种机制**：
> **它们的修法完全不同**（配置层 / 串行化 / 换池），而且**判据不同**。
> 把机制 3 误判成机制 1，就会去改 `cacheDir` / `TMPDIR` —— **改了半天，根因根本不在那里**。
> 我自己第三轮就犯了这个错：把「池不稳定」当成「测试不稳定」，又当成「文件丢失」。

#### 2.4.1 第四种形态：磁盘在变（**第五轮新增，机制③**）

**现象**：门禁报「缺 `coupon-state-machine.test.ts`」，但该文件**确实在磁盘上**，
且**集合级比对显示差集唯一、无顶替者**（不是「A 丢了 B 补上」）。

**证据链**（主理人 2026-10-22 实测）：
```
06:20:20  承钧落盘 coupon-state-machine.test.ts
06:20:38  承钧再落盘另一个测试文件
   ↓ 同期跑门禁
   → 报缺 coupon-state-machine.test.ts
   ↓ 磁盘稳定后
   → 连跑 6 次门禁 + 6 次 vitest → 全 38/38，零波动
```

**为什么 `singleFork` 治不了也不需要治**：
`singleFork` 解决的是「**多个进程**并发写同名缓存」，而机制③是「**测试文件在收集窗口内被创建/修改**」——
收集进程在某一刻扫到了目录快照，之后文件才落盘，或落盘后又被覆盖。
**这是时序问题，不是并发写冲突问题**，加串行化一点用都没有。

**关键性质：这不是「丢了文件」，是「快照与现实不同」**——
门禁报的是「收集快照里没有它」，而真相是「收集那一刻它还没落盘」。

**判别法（必须先做这一步，再谈并发/状态污染）**：

```
① 跑前记磁盘文件集合 S_before，跑后记 S_after
② S_before ≠ S_after  → 机制③（磁盘在变）→ 报 WARN，不是 ERROR
③ S_before = S_after  → 才往并发写 / 状态污染 / 池配置方向查
```

**⚠️ 最阴的地方：「多跑几次」在机制③存在时恰好会掩盖问题**——
磁盘稳定后连跑 6 次全绿，看起来「问题消失了」，
实际是**环境不再变化**了，不是门禁修好了。
**「多跑几次就绿了」不能作为「问题原因已查明」的证据**，
它只说明「现在这一刻磁盘是稳定的」。

**处置**：
- 门禁侧：缺的文件若 mtime 在「最近 N 分钟内」→ 报 **WARN + 提示「磁盘在变，可能是并发落盘」**，不报 ERROR
- 流程侧：**不要**在有人落盘的窗口跑门禁；或落盘方落盘后跑一次门禁确认

### 2.5 「测试失败」与「环境失败」必须分开

第三轮我看到「有 1~2 个测试失败」，判成「测试本身不稳定」→ **错**。
第四轮证明：那些失败**只出现在 threads 池下**，配置层四件套 **14/14 全绿**。

> **「有失败」有两种来源，现象几乎一样**：
> | 来源 | 特征 | 归属 |
> |---|---|---|
> | **测试失败** | `assertionResults[].status === 'failed'`，有 `failureMessages` | 业务代码 |
> | **环境失败** | 退出码 ≥ 128 / 报告缺失 / 收集数波动 | 工具链 |
>
> **区分方法**：
> 1. 看 `failureMessages` 是不是**断言消息**（`expected X to be Y`）而不是环境消息
> 2. 看**退出码**（≥128 = 崩溃）
> 3. 看**收集集合**（是否等于磁盘集合）
> 4. **在两个不同池下各跑一次** —— 若只在某一个池下失败，是环境问题
>
> **第 4 条是最省事的判别法，但要求你能切换配置**。这也是为什么 `vitest.config.ts` 的 `pool` 必须是**配置层固化**的：只有配置固定，才能做「A/B 对照」来区分环境与代码。

## 3. 断言的六维判据（第六轮定稿：主理人从五维扩到六维）

### 维度 ① 集合相等（不是数量相等）

```ts
const diskSet = new Set(diskFiles);        // 磁盘 find
const execSet = new Set(reporterFiles);    // JSON reporter testResults[].name
const missing = [...diskSet].filter(f => !execSet.has(f));  // 漏收集
const extra   = [...execSet].filter(f => !diskSet.has(f));  // 多收集
```

**为什么不能只比数量**：数量相等但内容不同 → 漏 A 收了 B，**仍是假绿**。
一个具体构造：磁盘新增 1 个测试文件的同时，某个旧文件因 EPERM 被丢 → `collected.length === diskFiles.length` 成立，但**新文件没跑、旧守门测试没跑**，门禁全绿。

**输出要求**：`missing` 必须**逐个文件名**打印，不得只报「31 ≠ 34」。

```
❌ [server] 收集缺失 2 个：
     src/middlewares/outbound-cipher-guard.test.ts   ← 守门测试：密文出参守卫
     src/domain/coupon.test.ts
```

### 维度 ② 实际执行集合相等（第三种丢文件形态）

> reporter 报的 ≠ 实际跑了。

reporter 的 `testResults[]` 里每一项带 `status` 字段（`passed` / `failed` / `pending`）。
- `status === 'passed' | 'failed'` → 该文件**确实被执行了**
- `status === 'pending' | 'skipped'` → **文件被报告了但没执行** —— 这在数量对账里完全看不见

```ts
const notExecuted = reporterFiles.filter(f => !['passed','failed'].includes(statusOf(f)));
if (notExecuted.length) errors.push(`[${pkg}] 报告了但未执行：${notExecuted.join(', ')}`);
```

**为什么这一维独立存在**：`numTotalTestSuites` 与 `testResults.length` 都会把 pending 文件算进去。只有 `status` 能区分「跑了」和「跳过了」。

### 维度 ③ 正交第二判据：`numFailedTests === 0` 且 `numPendingTests === 0`

**不依赖退出码**。通过「零失败 + 零跳过」反证无收集阶段失败。

> ⚠️ **注意：默认池的实测数据显示 `numFailedTests` 会是 1~2**（见 §2）。这说明存在**真实的不稳定测试**。
> 这不是收集门禁该管的，但**必须被报告出来**——否则「收集齐了」会掩盖「测试本身在抖」。

### 维度 ④ 禁列清单（**必须带「理由 + 处置」两栏**）

**格式（逐字，第五轮定稿）**：

```
禁列：<断言名> | 理由：<为什么测不到> | 若真发生：<去哪查 / 谁能发现>
```

**为什么必须是两栏而不是一栏**（主理人第五轮补的硬要求）：
只写「理由」不写「去处」，人看到禁列只会**跳过**——「这文件测不到，原因 X，算了」，
而不会去补。**理由解释了「为什么可以不测」，处置栏才回答「那出事时谁会发现」。**
没有处置栏的禁列 = 免检牌 = 一个永久的、无人认领的盲区。

**具体例子（本项目当前状态）**：

```
禁列：miniapp-user 包的任何测试文件 | 理由：该包磁盘上 0 个测试文件（2026-10-22 实测），
      npm test 脚本缺失 → 门禁无法对它断言收集完整性 | 若真发生：verify-all.cjs 的
      missingScriptIsWarn 分支会报「该包尚无 test 脚本（还没写测试）——待办，非失败」；
      谁会发现：CI 汇总表的 WARN 栏，不阻塞退出码
```

**语义（必须写进文档与代码注释）**：
> 禁列 = 「这个文件一旦消失，说明门禁本身失效」，**不是**「这个文件可以删」。

**为什么要有**：有些文件（如临时探针、一次性验证脚本）本来就不该被收集。允许禁列能避免「为了让门禁变绿而删文件」这种反向作弊。
**为什么必须带理由**：没有理由的禁列 = 免检牌 = 下一个文件可以随便进来。

### 维度 ⑤ 显示层自身正确性（**第五轮新增维度——显示层必须与断言层同源**）

**这条维度来自一次真实自相矛盾**（主理人实测撞到）：

```
check-test-collection.ts 报：「磁盘A=38 / 收集B=0 / 通过C=38」
```

**根因**（我已核到磁盘并确认修复）：
- `:281` 初始化 `r.collected = 0`
- `:309-314` 只给**局部变量** `collected` 赋了值，**从未赋值给 `r.collected`**
- **断言用的是局部 `collected.length`** → 判定正确
- **显示行印的是 `r.collected`** → 永远是 0

于是出现了「断言说 38、显示说 0、而通过数是 38」的三方矛盾——
**一个门禁在同一行输出里同时说「收集齐了」和「收集了 0 个」。**

**规格（硬要求）**：

```ts
// ❌ 违规：断言层与显示层取自两个不同的源
const collected = testResults.map(r => r.name);
if (collected.length !== diskFiles.length) { /* 断言用 collected ✅ */ }
render(`收集B=${r.collected}`);          // 显示用 r.collected ❌（永远是 0）

// ✅ 合规：断言与显示共用同一份数据源
const collected = testResults.map(r => r.name);
r.collected = collected.length;          // 落进 result 对象
if (collected.length !== diskFiles.length) { /* 断言用 collected ✅ */ }
render(`收集B=${r.collected}`);          // 显示用 r.collected ✅（同一个值）
```

**更严的写法（推荐）**：显示层**不读任何中间字段**，直接读断言层算出的那个局部变量：

```ts
const B = collected.length;               // 唯一真源
const A = diskFiles.length;
const C = passedFiles;
const verdict = (B === A && C === B) ? 'PASS' : 'FAIL';
render(`磁盘A=${A} / 收集B=${B} / 通过C=${C} → ${verdict}`);   // 全部来自 A/B/C
```

**为什么这一维是独立的**：
前四维保证「判定是对的」，第五维保证「**判定结果被如实显示**」。
两者是不同的失效面：前四维对而第五维错 → 门禁**行为正确但输出误导**——
人读输出会得出相反的结论（看到「收集B=0」会以为全崩了，看到「A=38」会以为没事）。
**「断言对、显示错」比「断言错」更危险**，因为断言错会让人去修，显示错会让人**不修**。

**自检方法（承钧落地时必须做）**：
故意让 `r.collected` 少赋一次值 → 输出的 A/B/C 三数必须**立刻自相矛盾**被看出来 →
说明断言层与显示层**不是同一个源**。恢复后三数必须一致。

**判据一句话**：**显示的每一个数字，都必须能追溯到断言用的那个变量。**

## 3.5 机制③「磁盘在变」的判别法（第五轮新增，承钧落地必做）

**放在 §3 之后、§4 之前的原因**：它不是一个独立断言维度，而是**判读前必须先做的一次排除**——
不先排除它，你会把「环境在变」误判成「门禁有洞」或「测试不稳定」，往错的方向修。

### 3.5.1 必须采集的两个快照

```ts
// 跑前
const before = new Set(findTestFiles(pkgDir));
// ... 跑 vitest，读报告 ...
// 跑后
const after = new Set(findTestFiles(pkgDir));

const diskChanged = before.size !== after.size
  || [...after].some(f => !before.has(f))
  || [...before].some(f => !after.has(f));
```

**注意**：`before.size !== after.size` **不够**——
删一个加一个总数不变，但集合变了。必须**双向差集都为空**才算没变。

**⚠️ 还要连顺序一起快照（第六轮主理人补的）**：
只比集合还不够，**顺序也要存**（排序后存一份有序列表）。

> **理由（主理人标注为「推理而非实测」）**：vitest 的**收集顺序变化本身**可能改变
> 「谁先写产物目录」的顺序，而 EPERM 竞态（机制 ②）**正是顺序敏感的**。
> 若磁盘集合没变但**收集顺序变了**，则「磁盘在变」这个判据会漏判。
>
> **判别口径**：
> - 集合变了（增/删） → 机制③「磁盘在变」，**确定**
> - 集合没变但**顺序变了** → **可疑**：磁盘内容可能变了（有人在编辑已有测试文件），
>   或 vitest 的收集顺序不稳定 → 归入「未解决」类，**报 WARN 并说明**
>
> **为什么不要求「内容哈希」**：主理人已明确「这一条我标为未解决，暂不要求你做
> （成本高、收益未定）」——内容级快照（hash 全量测试文件）在测试文件较大时开销明显，
> 且**改一个字符就变**，会把「有人在编辑」与「磁盘在变」混成一类噪声。
> **顺序快照是成本极低、收益明确的那一档**，故采纳。

### 3.5.2 判读矩阵

| 磁盘是否变化 | 缺文件 mtime | 判读 | 报什么 |
|---|---|---|---|
| **变了** | 任意 | 机制③：收集窗口内磁盘在变 | **WARN**（不是 ERROR）：「磁盘在变，本次结果不可信，请磁盘稳定后重跑」 |
| 没变 | **最近 N 分钟内** | 可能有人在改，也可能真丢 | **WARN**（带 mtime 与建议） |
| 没变 | 很久以前 | **真事故**：文件被静默丢弃 | **ERROR**（点名文件名） |
| 没变 | 无缺失 | 通过 | PASS |

### 3.5.3 mtime 判据的规格（主理人第五轮硬要求）

**断言 7.4（守门测试点名）的错误信息必须带磁盘文件 mtime**：

```
❌ [守门测试] src/middlewares/coupon-state-machine.test.ts（券状态机准入条件）
   在磁盘上存在但未被收集（mtime 2026-10-22 06:20:38 UTC）
   → 若上面文件的 mtime 是刚刚（几分钟内），多半是有人在落盘（机制③），
     请待磁盘稳定后重跑；若 mtime 很久以前，则是真丢了，
     请查 pool/singleFork/fileParallelism 配置
```

**⚠️ mtime 只作线索，不作判据——它绝不能把 ERROR 降级成 WARN 的万能借口。**

这条限制必须同时写进代码注释，因为它是**最容易被后来者滥用的一处**：
「mtime 很旧 → 报 ERROR」「mtime 很新 → 报 WARN」看起来很合理，
但它会开出一个后门：**任何人只要 `touch` 一下文件，就能让真事故降级成 WARN。**

**正确用法（三条同时成立）**：
1. mtime 只**改错误信息的措辞与建议**，**不改判定的严重级别**——
   严重级别由「磁盘是否变化 + 文件是否在磁盘上」决定
2. 磁盘变化 → WARN（因为结论不可信）；磁盘不变 → ERROR（因为结论可信）
3. 「最近 N 分钟」的 N 取值要写进常量并注明理由（建议 N=10 分钟；
   要大于「一次落盘 + 一次 vitest 启动」的典型耗时，否则刚落盘的文件会被误判为「很久以前」）

**当前承钧实现的现状（2026-10-22 实测）**：
`check-test-collection.ts:331-362` 已实现「错误信息带 mtime」，且**明确写了「mtime 只作线索不作判据」**，
并把「有人在落盘」的建议写进了消息文本。**这一项符合本规格**——
但它目前只做到「消息带 mtime」，**「磁盘是否变化」这个判别还没接进去**（见 §3.5.1 待办）。

### 3.6.1 归因纪律：**不采信「不是我引入」**（第六轮主理人裁定）

**主理人原话**（我第五轮报「不是我引入」时）：
> 「你说不是你引入，理由是『只改了 5 个 docs/*.md』。**这个理由不成立**（同一条错误推理的反面），
> 我改采信**你给的 mtime 证据**。」

**为什么「我只改了 X」不成立**：
它是**同一类推理的反面**——我第五轮用它证明「不是我」，它与「我改的」是同一种**单方自述**。
**审计报告的可信度建立在「不采信任何人的自述（包括我自己的）」上**，
而「我改了什么」正是自述的一种。

**可采信的归因证据（按强度排序）**：

| 证据 | 强度 | 说明 |
|---|---|---|
| **报错内容与我的改动范围的 grep 交集为空** | 强 | 错误消息里提到的符号/字段/文件，我改的范围内**一个都没有** |
| **被改文件的 mtime 晚于我的改动 mtime** | 强 | 文件在我改完之后**还在被别人改** |
| **实测能复现，且复现路径不经过我改的东西** | 最强 | 亲自跑一遍，看到同样的错 |
| 「我只改了 X」 | ❌ **不采信** | 单方自述，与被审计对象同一性质 |
| 「这看起来不像我干的」 | ❌ **不采信** | 观感不是证据 |

**本项目本轮的实际案例（示范怎么报）**：
第五轮我报了「两项类型检查 FAIL 不是我引入」，主理人驳回。**改报法**：
1. 错误内容 = `FunnelPage.tsx(182,20): Type 'number' is not assignable to type '"horizontal" | "vertical"'`
2. 我改的范围 = 5 个 `docs/*.md`；`grep -i "activity|elder|revenue|freshness|partition"` 对该错误 → **0 命中**
3. `FunnelPage.tsx` mtime **07:39:15** > `API-CONTRACT.md` mtime **07:28:52** → **在我改完之后还在被别人改**
4. 复跑后主理人确认该文件内容已变（承钧/映棠已收口）→ **中间态解释成立**

**这四条里没有一条是「我只改了 md」。**

**判据一句话**：
> **归因要靠「证据链」，不靠「声明」。**
> 「我改了什么」是声明；「错误内容与我的范围的交集为空 + mtime 顺序 + 能复现」是证据。

## 4. 「只增不减」基线

### 4.1 问题

硬编码期望值（`assert collected === 34`）在团队协作下**必然腐烂**：
- 有人加了第 35 个测试文件 → 门禁红了 → 他去改断言 → 改成了 35
- 这个过程里，**没有人再确认 35 是不是对的**

更要命的是：我本轮实测就撞上了——脚本启动时磁盘 34 个，跑到一半队友新增 1 个变成 35。**基线在测试过程中漂移。**

### 4.2 做法

```
基线文件：<pkg>/.tmp/collection-baseline.json
{
  "packages": {
    "server": { "files": ["src/...test.ts", ...], "updatedAt": "..." },
    ...
  }
}
```

**规则**：
1. 基线存 `.tmp/`（不入版本库，每次 CI 从零开始 → 不会掩盖「有人删了文件」）
2. **只增不减**：本次收集数 **<** 基线数 → **ERROR**（说明有文件被丢了）
3. 本次收集数 **> ** 基线数 → **自动更新基线**（有人加了新测试，正常）+ 打印 INFO
4. 本次收集数 **==** 基线数 → 但**集合不同** → **ERROR**（数量守恒但内容变了 → 有人换文件或丢了又多了）

> 关键：基线**不硬编码数字**，而是**集合的并集历史**。判定永远基于「集合是否 ⊆ 基线 ∪ 本次」。

## 5. 守门测试点名清单

### 5.1 问题：手写清单会腐烂

新增守门测试时，它**默认不在清单里** —— 于是它被丢时门禁不会红。

### 5.2 做法：清单从命名约定派生 + 手写只做加法

**派生规则（建议）**：
```ts
const GUARD_PATTERNS = [
  /-guard\.test\.ts$/,        // xxx-guard.test.ts
  /contract\.test\.ts$/,      // xxx-contract.test.ts
  /-wiring\.test\.ts$/,
  /enum-mirror\.test\.ts$/,
  /\.gates\.test\.ts$/,
];
// 派生集合 M = 所有匹配命名约定的测试文件
```

**双清单结构**：
- **派生清单 M**（自动，永不腐烂）：所有 `*-guard.test.ts` / `*contract.test.ts` 等必须被收集
- **手写清单 G**（人工，带理由）：契约没约定的关键守门测试（如 `coupon-deduct-wiring.test.ts`）

**断言**：`M ∪ G ⊆ execSet`，且 `M ∪ G ≠ ∅`（防空规则导致派生集为空而恒真）。

**手写清单 G 的每条必须带 `guards` 字段**（守护什么），理由缺失即门禁自检失败——理由是人读的，也是下一个人的交接文档。

### 5.3 主理人提的缺口：「单跑红、全跑绿」

> 守门测试**单独跑是红的**，全量跑是绿的 —— 说明它的断言依赖了别的测试留下的状态。

**检测方法**：
1. 全量跑 → 记录守门测试结果（绿）
2. **单独跑**该守门测试 → 记录结果
3. **两者结果不一致** → ERROR：`守门测试 X 单跑与全跑结果不一致，存在跨测试状态依赖`

这一条必须**逐个守门测试跑**，成本高。**建议只对 G（手写清单）做**，M（派生清单）抽样。

## 6. 三态自证（反例必须真红）

**目的**：证明这条门禁**有牙齿**，不是恒真。

### 6.1 自证流程

```
① 记录打破前的收集数 B_before 与各守门测试结果
② 故意打破：把某个守门测试的断言改成必然失败
③ 重跑 → 观察
④ 撤销 → 重跑 → 观察
```

### 6.2 三态断言（主理人补的第三条，是关键）

```
打破后必须同时满足：
  ① 收集数 === 打破前收集数        （文件没被丢）
  AND 出现明确的「断言失败」信息     （不是「解析错误」/ 不是「未收集」）
  AND 恢复后：收集数回到原值 + 全绿
```

**为什么 ① 不可省**（主理人指出的陷阱，我复述）：
如果「打破」动作本身让该文件**无法被收集**（比如在 test 文件顶部加一行 `import xxx from 'nonexistent'` 导致解析失败），那么：
- vitest 会在**收集阶段**就报解析错误
- 根本进不到断言阶段
- 你看到的「红」是**解析错误**，不是**断言失败**

这就是第三种解释：**断言没牙齿 / 破坏没生效 / 破坏导致文件无法收集**。三者现象都是「红」，必须用 ① + ② 联合区分。

**推荐打破手法**（避开解析失败）：
- ✅ 改断言的期望值：`expect(x).toBe(1)` → `expect(x).toBe(999)`
- ✅ 加一条必然失败的断言：`expect(true).toBe(false)`
- ❌ 引入语法错误 / 不存在的 import（会走解析失败路径）

### 6.2.1 三态守门（第五轮定稿，主理人硬要求）

**主理人原话**：**三态必须区分「还没创建」vs「被丢弃」**——
① 磁盘不存在 → WARN 待办；② 在磁盘但未被收集 → ERROR 真事故；③ 已收集 → PASS。
**判据一句话：只有 ② 才是假绿事故。**

**为什么不能只做两态**（这是本项目反复追打的同一个病根）：
两态时，「还没写」与「写了但没跑」被混成一类 ERROR。
后果是：**真事故淹没在噪声里** → 报警信号被稀释 → **门禁被静音**。
一个天天报 3 条「守门测试还没写」的 CI，一周后没人再看它的红灯——
**这跟没有门禁是同一个效果，但外观上看着有门禁**（更危险，因为它给了虚假的安全感）。

**三态表（实现必须逐字对齐）**：

| 态 | 判据 | 严重级别 | 消息必须写什么 |
|---|---|---|---|
| ① **还没创建** | 文件**不在磁盘上** | **WARN** | 「在磁盘上尚不存在 —— 待办：守门测试未创建」+「尚未创建 ≠ 被丢弃；一旦创建后未被收集，才升级为 ERROR」 |
| ② **被丢弃**（假绿事故） | 文件**在磁盘上**但**未被收集** | **ERROR** | 文件名 + 守卫名 + **磁盘 mtime** + 「若 mtime 是刚刚，多半是机制③（磁盘在变），待稳定后重跑；若很久以前，则是真丢了，查 pool/singleFork/fileParallelism」 |
| ③ **已收集** | 文件在磁盘上**且**在 `collectedFiles` 里 | **PASS** | 无（静默通过） |

**判定的先后顺序（顺序错了会误判）**：

```
① 先判「文件在磁盘上吗」  → 不在 = 态① WARN，结束
② 再判「在 collectedFiles 里吗」→ 在 = 态③ PASS，结束
③ 都不满足 = 态② ERROR（这是唯一会报 ERROR 的分支）
```

**⚠️ 态② 里还嵌了一个判别**（来自 §3.5）：
态② 的 ERROR 判定要**先看磁盘是否在变**——
磁盘在变 → 结论不可信 → 降为 WARN 并说明「请磁盘稳定后重跑」；
磁盘不变 → 真事故 → ERROR。

**为什么态② 的消息必须带 mtime**：不带 mtime，收到的人无法判断是「有人正在改」还是「真丢了」，
两种情况的处置完全不同（等 vs 查配置）。**消息不带处置信息 = 把判断成本推给了收到消息的人。**

**当前承钧实现的现状（2026-10-22 实测，`check-test-collection.ts:390-410`）**：
三态**已实现**，且注释里明写了「① 还没写 / ② 写了但没跑 / 只有 ② 才是假绿事故」，
态① 的消息也带「尚未创建 ≠ 被丢弃」这句。**这一项符合本规格。**
唯一未接的是 §3.5.1 的「磁盘是否变化」判别（态② 里还没区分「磁盘在变」与「真丢了」）。

## 7. 归因表：错→对 与 对→错 分开

| 变化 | 归因 | 动作 |
|---|---|---|
| 错 → 对 | 修复生效 | **接受** |
| 对 → 错 | **修复引入了新的丢失路径** | **阻塞，立即调查** |

**「对→错」比「错→对」更重要** —— 它意味着给出的方案本身有害。

**实现**：
```
基线（上一轮）: 收集集合 C_prev
本轮:            收集集合 C_now
若 C_prev ⊆ C_now 且 C_now ⊊ 应收集集合   → 「对→错」 → ERROR（阻塞）
若 C_prev ⊄ C_now 且 C_now 仍 ⊊ 应收集集合 → 「错→对（部分）」 → ERROR（继续修）
```

**只有「C_now === 应收集集合」且「C_prev ≠ C_now」时才算「错→对」** —— 即：真的修好了，且不是靠删文件修好的（删文件会让 C_now ⊂ 磁盘集合，被维度 ① 拦下）。

### 8.1 「连续跑 ≥3 次」的判据

```
3 次全部满足「集合 == 磁盘集合」且「无缺失」 → 判定通过
任意一次缺失 → 判定失败，且必须打印那一次的缺失文件名
```

**不得**用「3 次里有 2 次通过」这种多数决 —— 丢文件是概率事件，多数决会放过 1/3 的丢失率。

### 8.2 连续跑的实现成本

server 一次全量 ≈ 25s，3 次 ≈ 75s。**建议**：
- 本地/CI 门禁：**跑 1 次**（快速反馈），但用**基线文件**做「只增不减」跨次校验
- 夜间/发布前：**跑 3 次**（随机性只能靠重复暴露）

> 这不是妥协，是把「随机性」的成本放在合适的地方。**关键是跨次有基线可比**，而不是每次都跑 3 遍。

### 9.2 两种丢文件机制的判别结果

- **机制 1（EPERM 写盘失败）**：清缓存后**仍不收集**
- **机制 2（并发写同名缓存覆盖）**：清缓存后**恢复全收集**

**本轮实测（server）**：清缓存后重跑 `pool=forks` → 35/35/35 稳定，**未复现丢失**。
→ 结论：**当前 server 包的收集已由配置层（forks + singleFork）稳定住，机制 1/2 均未触发**。
→ 但**不能据此断言根因已消除**：机制 2 的特征是「缓存目录有并发写」，`singleFork` 从根上消除了并发（不只是清缓存能修），这才是稳定的原因。

## 10. 附：可直接套用的判定伪码

```ts
// ── 0. 磁盘快照（跑前）—— 机制③ 判别的必要输入
const diskBefore = new Set(findTestFiles(pkgDir));   // 相对路径，posix 分隔

// ── 1. 取磁盘集合（= diskBefore，本段沿用）
const disk = [...diskBefore];
const diskSet = diskBefore;

// ── 2. 跑测试，拿 reporter
const raw = JSON.parse(readFileSync(jsonOut, 'utf8'));
const execSet = new Set(raw.testResults.map(r => rel(r.name)));
const statuses = new Map(raw.testResults.map(r => [rel(r.name), r.status]));

// ── 3. 维度①：集合相等
const missing = [...diskSet].filter(f => !execSet.has(f));
const extra   = [...execSet].filter(f => !diskSet.has(f));
if (missing.length) ERROR(`漏收集 ${missing.length} 个：${missing.join(', ')}`);
if (extra.length)   WARN(`多收集 ${extra.length} 个：${extra.join(', ')}`);

// ── 4. 维度②：被执行（不是仅被报告）
const notRun = [...execSet].filter(f => !['passed','failed'].includes(statuses.get(f)));
if (notRun.length) ERROR(`报告了但未执行：${notRun.join(', ')}`);

// ── 5. 维度③：正交判据
if (raw.numFailedTests > 0)   ERROR(`有 ${raw.numFailedTests} 个测试失败`);
if (raw.numPendingTests > 0) ERROR(`有 ${raw.numPendingTests} 个测试被跳过`);
// ⚠️ 绝不用 numTotalTestSuites 当文件数

// ── 6. 维度④：禁列（带理由）
for (const b of DENYLIST) {
  if (!b.reason?.trim()) ERROR(`禁列条目 ${b.file} 缺理由`);
}

// ── 7. 守门点名
const M = deriveGuardFiles(disk);                  // 命名约定派生
const G = MANUAL_GUARDS;                           // 手写，带 guards
if (M.length + G.length === 0) ERROR('守门清单为空 —— 派生规则失效或清单被清空');
for (const f of [...M, ...G.map(g => g.file)]) {
  if (!execSet.has(f)) ERROR(`守门测试未被收集：${f}`);
}

// ── 8. 只增不减基线
const baseline = loadBaseline(pkg);
if (baseline && execSet.size < baseline.size) {
  ERROR(`收集数 ${execSet.size} < 基线 ${baseline.size} —— 疑似丢失`);
} else {
  saveBaseline(pkg, union(baseline, execSet));
}

// ── 9. 归因：对→错 阻塞
if (baseline && !isSubset(baseline, execSet) && missing.length === 0) {
  ERROR('上一轮能收集的文件本轮未收集 —— 「对→错」，修复引入了新丢失路径');
}

// ── 10. 磁盘快照（跑后）+ 机制③ 判别
const diskAfter = new Set(findTestFiles(pkgDir));
const diskChanged =
  diskBefore.size !== diskAfter.size
  || [...diskAfter].some(f => !diskBefore.has(f))
  || [...diskBefore].some(f => !diskAfter.has(f));
// ⚠️ 只比 size 不够：删一个加一个总数不变，但集合变了 → 必须双向差集都为空

// ── 11. 维度⑤：显示层与断言层同源
//    断言与显示**共用同一批局部变量**，不得一个用 r.xxx 一个用局部变量
const A = diskSet.size;
const B = execSet.size;
const C = passedFiles;
const verdict = (missing.length === 0 && B === A && C === B) ? 'PASS' : 'FAIL';
render(`磁盘A=${A} / 收集B=${B} / 通过C=${C} → ${verdict}`);
// ❌ 违规写法：render(`收集B=${r.collected}`) —— r.collected 若未赋值则永远 0
//    症状：同一行输出里「A=38 / B=0 / C=38」自相矛盾（2026-10-22 实测）

// ── 12. 态② 里的机制③ 区分（配合 §3.5.2 判读矩阵）
//    缺文件在磁盘上但未被收集时：
for (const f of missing) {
  const mt = mtimeOf(f);                        // 磁盘 mtime
  const mtMsg = `（mtime ${mt} UTC）`;
  if (diskChanged) {
    WARN(`[机制③] ${f} 在磁盘上但未被收集${mtMsg} —— 磁盘在收集窗口内变化，`
       + '本次结论不可信，请待磁盘稳定后重跑');
  } else {
    ERROR(`[真事故] ${f} 在磁盘上但未被收集${mtMsg} —— 磁盘未变化，是真的丢了；`
        + '请查 pool / singleFork / fileParallelism 配置');
  }
}
// ⚠️ mtime 只改措辞与建议，**不改严重级别** —— 否则 `touch` 一下就能把真事故降级成 WARN
```

### 10.1 伪码的三个易错点（照抄时最常错的地方）

| 易错点 | 错误写法 | 正确写法 | 症状 |
|---|---|---|---|
| 磁盘变化判定 | `diskBefore.size !== diskAfter.size` | 双向差集都为空才算没变 | 删一个加一个 → 误判「没变」 |
| mtime 的作用 | `mtime 很新 → WARN` / `mtime 很旧 → ERROR` | 严重级别由「磁盘是否变化」决定，mtime 只进消息文本 | `touch` 文件即可把真事故降级 |
| 维度⑤ 的数据源 | 断言用 `collected.length`，显示用 `r.collected` | 两处都用同一个局部变量 | 输出「A=38 / B=0 / C=38」 |

## 11. 「验证手段本身可能失效，而它看起来有效」（第五轮新增，主理人亲历）

### 11.1 事故原委

主理人写 `scripts/verify-all.cjs` 时，文件头 `/**` 忘闭合 `*/`：

```ts
/**
 * ... 注释开始
const GATES = [ ... ];     // ← 整段被吞进注释
const results = [];
function run() { ... }     // ← 也被吞
// 一直到第 72 行才遇到 */ 或意外结束
```

**后果**：
1. 三行 `const` 声明全被吞进注释 → 顶层变量全 `undefined`
2. **`node --check` 通过** —— 因为被吞掉的代码**语法上完全合法**
3. 但**代码根本没执行** —— 顶层 `const GATES` 从未声明，脚本运行即 `ReferenceError`

### 11.2 为什么 `--check` 查不出来

`node --check` 只做**语法**检查，不做**语义**检查。
「注释未闭合」是**语法合法但语义丢失**的一类故障：
被吞掉的代码从语言视角看根本不存在，所以它既不违反语法，也不产生任何告警。

**`--check` 通过 ≠ 代码被执行了。**

### 11.3 可靠判据

| 手段 | 能查到什么 | 查不到什么 |
|---|---|---|
| `node --check` | 语法错误（括号不配、缺分号…） | **注释未闭合吞代码**、变量未声明、逻辑错 |
| `tsc --noEmit` | 类型错误 + 未使用变量 | 运行时才暴露的路径 |
| **跑一次并看输出** | **「这段代码到底执行了没有」** | — |

**结论：可靠判据是「跑一次并看输出」，不是「静态检查通过」。**

### 11.4 对本报告的直接约束（这条最要紧）

这一条不只是代码规范，它**直接限制了「已验证 / 未发现问题」这类结论的可信度**：

> 写「已验证」「未发现问题」时，**验证手段本身可能失效而它看起来有效**。
> 所以每条「已验证」都必须能回答两个问题：
> ① **我跑的是什么命令？**（具体到参数与工作目录）
> ② **输出是什么？**（实际输出，不是「通过了」三个字）

**为什么这条对门禁审计特别致命**：
门禁审计的全部价值建立在「门禁真的会红」这个假设上。
如果门禁脚本因为一个未闭合的注释而**从未真正执行过断言**，那么：
- 它一直报「全绿」
- 它的退出码是 0
- CI 一直是绿的
- **而它一个断言都没跑过**

这叫「**门禁在检查范围外**」——本轮 8 条线索的第 1 条。
**注释未闭合是它最隐蔽的一种形态**：因为门禁文件本身是存在的、是可运行的、退出码是正确的。

### 11.5 落地要求（承钧）

- [ ] `check-test-collection.ts` 与 `verify-all.cjs` **必须跑一次并把输出贴进自证记录**（不是「`node --check` 通过」）
- [ ] 自证记录里要有「脚本实际打印了几行输出」这一项——
      **一行都不打印的脚本 = 它没执行到任何断言**
- [ ] `verify-all.cjs` 的门禁表里，每个 `expect: 'exit0'` 的门禁，
      **必须能区分「跑完了且通过」与「启动就崩了但退出码恰好是 0」**
      （现在的 `status === null` 分支只覆盖「进程没起来」，不覆盖「跑了但没跑完」）
- [ ] 建议在每条门禁的判读里加一条**最弱断言**：
      脚本必须**至少打印一行自己的结论**（如「检查了 N 个包，ERROR 0，WARN 2」），
      聚合入口据此判断「它真的跑过了」——
      **「没有输出」= 「没跑」**，这是最便宜也最可靠的存活判据

### 11.6 与 wiki 的同源关系

主理人已把这条写进 `D:/wiki/Learning/insight-assert-right-display-wrong-2026-10-22.md`，
其中列了三条同源故障：

1. **断言对、显示错**（→ 维度⑤）
2. **注释未闭合吞代码**（→ 本节）
3. **两态当三态**（→ §6.2.1）

**三条的共同结构**：
> **「看起来对」与「实际上对」之间没有可见的差别**——
> 所以必须有一层**主动去制造可见差别**的机制
> （自证 / 显示层同源 / 三态区分），
> 而不能靠「读起来没问题」。

## 12. 架构决策：`check-test-collection.ts` 是否改成读 `verify-all.cjs` 的报告（第五轮，主理人征询）

主理人原问：

> 保持现状（`check-test-collection.ts` 自己跑，崩溃时只能靠 mtime 线索），
> 还是改成读报告（架构更干净，但要等聚合入口先跑）？

### 12.1 先纠一个前提（我实测了）

主理人的理由是：「`check-test-collection.ts` 用 `execFileSync` 起 vitest，崩溃时它自己也会崩，拿不到退出码」。

**实测结论：这个前提不成立。** 探针（`.tmp/probe-execfile-crash.cjs`）：

```
exit139 => 父进程存活，捕获异常：status= 139  signal= null  code= undefined
segv    => 父进程存活，捕获异常：status= 1    signal= null  code= undefined
父进程执行到末尾 —— 说明 execFileSync 不会让父进程连带崩溃
```

`execFileSync` 在子进程非零退出时**抛异常而不是连带崩溃**，且异常对象上带 `status`（= 子进程退出码）。
所以「崩溃时拿不到退出码」不是 `execFileSync` 的限制，**是当前实现把 catch 写空了**：

```ts
// 现状（check-test-collection.ts:257-265）
try {
  execFileSync(...);
} catch {
  // EPERM 会让退出码非 0，但 JSON 报告通常仍已写出，故不直接判失败
}
```

**`catch {}` 里没有 `e.status`** → 退出码信息被**主动丢弃**了。
修法是 3 行（接住 `e.status` + 判崩溃形态），**不需要改架构**。

### 12.2 我的建议：**保持现状（自己跑），但把退出码判据接上**

理由三条：

**① 「退出码判据只在一处实现」的正确解法不是「合并成一处进程」，而是「判据写成共享模块」。**
判据重复实现的解法是抽函数，不是抽进程。现在 `verify-all.cjs` 的 `:417-425` 已经有那份判据，
把它抽成 `apps/server/scripts/lib/exit-status.ts` 之类，两边共用——**这是 1 小时的活**，
而改成读报告是**改两个脚本的数据流契约**，风险大得多。

**② 「自己跑」是这条门禁的独立可用性保障。**
`npm run test:check:collection --workspace @linban/server` 必须能单独跑。
改成读报告后，它就**依赖聚合入口先跑过**——而聚合入口的第一步**就是它自己**。
这会形成一个**自举依赖**：要么死循环，要么必须把「跑 vitest」这一步再拆成一个独立脚本。
**为一个 8 秒的门禁引入一条数据流依赖，不划算。**

**③ 现在的重复开销可接受，而且不是纯浪费。**
实测：`server` 单次全量 vitest ≈ **8.4 秒**（我实测 `npx vitest run --reporter=json`，real 8.43s）。
`verify-all.cjs` 里「收集完整性」和「服务端单测」两条各跑一次 = 约 17 秒。
**这 8 秒买的是「收集门禁能在没有聚合入口的情况下独立给出可信结论」**——我认为值。

### 12.3 但有一个真问题必须解决（与架构无关）

`check-test-collection.ts` 的 `catch {}` **把退出码丢了**，导致：
- vitest **整体崩溃**（native 崩 / 启动失败）→ 报告没产出 → 脚本报「vitest 未产出 JSON 报告」
- 这条消息**看不出是崩溃还是断言失败** → 与主理人建 `verify-all.cjs` 时要解决的**是同一个问题**

**修法（承钧，3 行）**：

```ts
let exitCode: number | null = null;
try {
  execFileSync(...);
} catch (e: any) {
  exitCode = typeof e?.status === 'number' ? e.status : null;
  // 崩溃形态：>=128（POSIX 信号）或 3221225477 / -1073741819 / 0xC0000005（Windows）
  const isCrash = exitCode !== null
    && (exitCode >= 128
      || exitCode === 3221225477 || exitCode === -1073741819 || exitCode === 0xC0000005);
  if (isCrash) {
    errors.push(`[${pkg}] vitest 进程级崩溃（退出码 ${exitCode}）—— 不是断言失败，`
      + '排查方向：pool 配置 / 原生模块 / 内存');
  }
  // 若是断言失败（退出码 1 且报告已产出），由维度①~⑤ 正常判定
}
```

### 12.4 最终建议（一句话）

> **保持 `check-test-collection.ts` 自己跑**；
> 把退出码判据抽成**共享模块**（`verify-all.cjs` 与它共用），
> 并把 `catch {}` 补成接住 `e.status` —— **这是 3 行改动，不动架构**。
>
> 判据共享用抽函数，**不用抽进程**。

**如果将来真的出现「跑两遍太慢」的痛点**（比如 server 包涨到 60 秒+），
再评估改成读报告——但那时要一并解决「独立可用性」与「自举依赖」两个问题，
不能只想着省那 8 秒。
