## 📖 项目简介

「邻伴」是一个面向中国老龄化社区的陪伴服务匹配平台，通过数字化手段连接：

- **老人及其家属**（需求方）—— 发布陪伴需求（就医陪同、日常照料、情感交流等）
- **陪聊员/志愿者**（供给方）—— 提供陪伴服务并获得合理报酬
- **社区运营者**（管理方）—— 监控服务质量、调配资源、处理异常

平台核心能力包括：

| 模块       | 功能                                   |
| -------- | ------------------------------------ |
| **智能匹配** | 基于老人画像、陪聊员技能、地理位置、时间窗口的多因子匹配算法       |
| **订单流转** | 预约 → 派单 → 接单 → 服务中 → 完成 → 评价的全生命周期管理 |
| **风控体系** | SOS 紧急求助、举报机制、异常行为检测、黑名单联动           |
| **营收分析** | 多维度营收报表（按社区/渠道/时间）、分账结算、优惠券核销        |
| **归因追踪** | 触点采集 → 漏斗分析 → 渠道 ROI 评估，支持投放决策优化     |

## 🧭 战略定位

### 一句话定位

以**亲邻社区媒体**（门禁灯箱 + 单元门灯箱 + 开门 App）为信任与流量底座，在广州单城试点**四位一体**陪伴匹配平台，先切**就医陪诊与情感陪伴**两类刚需，用「保险/长护险支付 + 子女付费 + 街道政府采购买单」组合变现，跑通最小闭环后向全国复制。

### 三个核心判断

| # | 判断 | 工程含义 |
|---|------|---------|
| 1 | Papa 的百亿估值证明「情感陪伴」是真实刚需且可规模化，但其「商保支付 + C 端付费」的美国土壤在中国不完全具备 → **必须本土化** | 支付方多元（子女代付为主 + 街道采购 + 保险试点） |
| 2 | 中国老人对**非医疗陪伴**付费意愿低，对**就医陪诊/专业护理**付费意愿高 | 主切高意愿品类，纯聊天陪伴不作为主变现路径 |
| 3 | 亲邻社区媒体是天然信任与获客基础设施 | 获客成本结构性低于纯线上陪诊平台 |

### 市场基本盘

| 指标 | 数值 | 来源 |
|---|---|---|
| 60+ 人口（2024 末） | **3.10 亿**，占 22.0% | 国家统计局 2024 公报 |
| 银发经济规模（2025） | **≈9 万亿元** | 银发经济蓝皮书(2025) |
| Papa 估值 | **14 亿美元**（≈100 亿人民币），累计融资 2.4 亿美元 | Papa 官方披露 / 胡润全球独角兽榜 |
| 60+ 人口预测（2035） | **4 亿+**，占比约 30% | 多机构一致预测 |
| 「情感/陪伴（非医疗）」细分 | 供给极少，**无权威规模** | 蓝海缺口 = 本项目切入点 |

> Papa 已服务超 **260 万次**，会员医疗费用降 9%、住院减 18%、专业护理设施使用减 22% —— 陪伴经济的商业闭环已被验证。

### 竞争格局

| 模式 | 代表 | 机制 | 付费 | 局限 |
|---|---|---|---|---|
| 时间银行 | 南京时间银行、上海「沪助养老时光汇」 | 低龄帮高龄，存时光币未来兑换 | 免费互助 | 跨区域兑换难，年轻人少 |
| 陪诊平台 | 国融乐养、蓝豚医陪、向阳陪诊团 | 持证陪诊师 1 对 1 | 付费/公益 | 获客贵，信任建立慢 |
| 共享儿女 | 自媒体议题 | 概念阶段 | — | 未成规模平台 |
| **邻伴** | 亲邻资源 + 四位一体 | 匹配引擎 + 社区媒体信任锚 | 保险+子女+政府+导流 | 待广州 MVP 验证 |

> **政策窗口**：北京「全国助医陪诊银发公益行动」三年计划覆盖京沪广深蓉郑——**广州已被列入国家级陪诊试点城市**。

### 四位一体供给模型

| 角色 | 人群 | 服务内容 | 付费方式 | 信任机制 |
|---|---|---|---|---|
| **共享孙辈（共享儿子）** | 大学生/年轻职场 | 陪聊、科技教学、陪逛、代跑腿 | 付费（时薪） | 实名 + 培训 + 双向评价 |
| **时间银行** | 低龄健康老人 | 陪聊、简单家务、陪诊 | 积分兑换（未来） | 社区熟人背书 |
| **社区志愿者** | 在地热心居民 | 定期探访、节日陪伴 | 荣誉 + 补贴 | 街道/居委会认证 |
| **专业陪护** | 持证陪诊师/护理员 | 就医陪诊、康复辅助、健康监测 | 付费（高客单） | 资格证 + 保险 + 平台担保 |

> 供给角色（`companion_role`）、服务类型（`service_type`）、能力标签（`tags`）三者**正交**——
> 「一位陪聊员是什么角色」「提供什么服务」「会什么方言棋牌」是三个独立维度。工程落点见
> [ARCHITECTURE.md](docs/ARCHITECTURE.md)。

### 护城河：亲邻社区媒体

| 亲邻资产 | 数据 | 在本项目用途 |
|---|---|---|
| **开门 App** | 实名注册 3,000 万+，月活 2,000 万+，单月人脸开门过亿次 | 流量入口 + 实名信任 + 青年/老人双侧触达 |
| **单元门灯箱** | 330×558mm 静态灯箱 + 语音，日均到达率 87%，日均接触 3.8 次 | 线下获客 + 品牌信任锚 + 志愿者招募 |
| **广告门** | 全国 70,000+ 小区，覆盖 3 亿城镇家庭，占 77% 社区门禁市场 | 规模化复制时的低成本曝光网络 |
| **社区团购私域** | 既有社群 | 子女侧转化 + 银发消费导流 |
| **社区数据资产（5V）** | 67,651 点位 / 220 城市 | 精准匹配与选点 |

> **护城河逻辑**：Papa 在美国最大成本是获客与信任建立；亲邻用「门禁物理触点 + 实名 App」
> 把这两件事变成**既有基础设施**，使单位获客成本与信任建立成本显著低于纯线上陪诊平台。

### 变现结构

| 收入流 | 支付方 | 可行性 | 备注 |
|---|---|---|---|
| 保险/长护险合作 | 商保、长护险试点 | 中（需效果数据） | 对标 Papa 保险闭环 |
| **街道/政府采购** | 民政、社区 | **高（政策刚需）** | 广州已入国家级陪诊试点 |
| **C 端子女代付** | 老人子女 | **高（情感消费）** | **主变现路径**，月订阅 + 单次佣金 |
| 银发消费导流 | 康养/辅具/文旅 | 中 | 复用亲邻社区团购私域 |
| 媒体资源反哺 | 内部摊薄 | — | 亲邻门禁媒体获客 ≈ 0 |

### 广州单城试点路线

| 阶段 | 主题 | 关键动作 |
|---|---|---|
| **0–3 月** | 冷启动 | 动员低龄老人建时间银行；招募首批持证陪诊师；门禁媒体曝光；**跑通 50 单陪诊** |
| **3–6 月** | 跑通 | 子女订阅上线；对接 1–2 街道采购；匹配引擎迭代；**月均 300+ 单** |
| **6–12 月** | 复制 | 扩至 5–10 社区；谈长护险/商保试点；沉淀降费数据 |

- **选点**：越秀/海珠等老城区（高龄独居密集）做冷启动；珠江新城周边高端社区（子女付费能力强）做付费验证
- **北极星指标**：月均成功匹配单量
- **安全红线**：安全事件数 **须为 0**

## 🚀 快速开始

### 前置要求

- Node.js >= 20
- npm >= 10
- Docker & Docker Compose（本地开发可选）
- MySQL 8.0（本地或远程）

### 安装依赖

```bash
npm install
```

### 本地启动

#### 方式一：Docker Compose（推荐）

```bash
docker-compose up -d
```

这将启动 MySQL 容器并自动执行初始化脚本（字符集、时区）。

#### 方式二：手动启动

1. **配置环境变量**

   在 `apps/server/.env` 中设置：
   ```env
   DATABASE_URL="mysql://user:password@localhost:3306/linban"
   JWT_SECRET="your-secret-key"
   ```
2. **数据库迁移**
   ```bash
   cd apps/server
   npx prisma migrate deploy
   npx prisma generate
   ```
3. **启动各服务**
   ```bash
   # 后端
   npm run dev --workspace @linban/server

   # 管理后台
   npm run dev --workspace @linban/admin-web

   # 小程序（需 H5 预览模式）
   npm run dev:h5 --workspace @linban/miniapp-user
   ```

## ✅ 门禁系统（Phase 3 交付）

本项目实施了严格的 **16 项聚合门禁**，确保代码质量与数据一致性。所有门禁通过单一入口 `scripts/verify-all.cjs` 执行。

### 运行门禁

```bash
# 全量门禁
npm run verify:all

# 列出所有门禁项
npm run verify:list

# 只跑特定分组
npm run verify:all -- --only=typecheck,test,collect
```

### 门禁分组

| 分组          | 包含项                                     | 说明                                      |
| ----------- | --------------------------------------- | --------------------------------------- |
| `collect`   | 收集完整性（server vitest）                    | 守门测试被静默丢弃检测                             |
| `test`      | 服务端/管理后台/陪聊员端/用户端单测                     | 领域纯函数 + 状态机 + 契约守卫回归网                   |
| `typecheck` | 四端 TypeScript 检查                        | shared / server / admin-web / miniapp-* |
| `doc`       | 文档↔代码配置一致性                              | 段 1-7 号段登记、迁移链、配置域分组键集                  |
| `db`        | Prisma schema 校验 / 客户端生成 / 迁移状态 / 存量券回填 | 部分需 DB 可达                               |

### 退出码分级

| 退出码 | 含义                                 |
| --- | ---------------------------------- |
| 0   | 全部通过                               |
| 1   | 存在真失败（断言失败）                        |
| 2   | 疑似收集阶段失败（EPERM / 进程崩溃 / B>A 口径不一致） |
| 3   | 有跳过项且 `--strict` 模式                |

### 关键设计原则

1. **收集完整性断言必须是第一步** —— 防止守门测试被静默丢弃导致报告全绿但关键守卫没跑
2. **不依赖 DB 就能跑通必需门禁** —— PR 门禁可在无数据库环境下执行
3. **三态区分** —— 「还没写」（WARN）≠「写了但没跑」（ERROR）≠「正常」（PASS），只有后者才是假绿事故
4. **B > A 判据** —— 报告收集数比磁盘文件数还多时，判定为两侧口径不一致（非并发污染），点名差集文件

详细规范见 [docs/GATE-COLLECTION-SPEC.md](docs/GATE-COLLECTION-SPEC.md)。

## 🤝 贡献指南

### 开发流程

1. Fork 本仓库
2. 创建特性分支 (`git checkout -b feature/AmazingFeature`)
3. 提交更改 (`git commit -m 'Add some AmazingFeature'`)
4. 推送到分支 (`git push origin feature/AmazingFeature`)
5. 开启 Pull Request

### 代码规范

- TypeScript 严格模式，禁止 `any`
- 所有公共 API 必须有 JSDoc 注释
- 新增功能必须配套测试用例
- 提交前运行 `npm run verify:all` 确保门禁通过

### 门禁纪律

- **破坏法自证必须先验收集完整** —— 磁盘数 === 报告数 === 守门点名全绿，破坏才有意义
- **门禁必须声明「不覆盖什么」** —— 禁列要带「理由 + 若真发生去哪查」两栏
- **「已验证」三问**：跑的是什么命令 / 输出是什么 / 谁复核过
